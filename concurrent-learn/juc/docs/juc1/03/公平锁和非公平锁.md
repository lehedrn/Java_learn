# 公平锁和非公平锁

## 概念定义

### 公平锁 (`Fair Lock`)
公平锁是一种线程调度策略，它确保线程按照请求锁的先后顺序获得锁资源。当多个线程同时竞争同一个锁时，等待时间最长的线程优先获得锁，遵循先进先出(`FIFO`)原则。

### 非公平锁 (`Non-fair Lock`)
非公平锁不保证线程获取锁的顺序，允许后来的线程"插队"获取锁资源。即使有线程已经在等待队列中，新来的线程也可能直接获得锁。

## Java中的实现

在Java中，主要通过 `ReentrantLock` 类来演示公平锁和非公平锁的区别：

```java
// 创建公平锁
ReentrantLock fairLock = new ReentrantLock(true);

// 创建非公平锁(默认)
ReentrantLock nonFairLock = new ReentrantLock();
// 或者显式声明
ReentrantLock nonFairLock2 = new ReentrantLock(false);
```


## 特性对比

| 特性 | 公平锁 | 非公平锁 |
|------|--------|----------|
| 获取锁顺序 | 严格按照申请顺序(FIFO) | 不保证顺序，可插队 |
| 性能表现 | 相对较低 | 相对较高 |
| 线程饥饿 | 基本不会发生 | 可能发生 |
| 实现复杂度 | 较高 | 较低 |

## 工作原理

### 公平锁工作流程
1. 线程尝试获取锁
2. 如果锁被占用，线程进入等待队列尾部
3. 当锁释放时，队列头部的线程优先获得锁
4. 保证了严格的 `FIFO` 顺序

### 非公平锁工作流程
1. 线程尝试直接获取锁
2. 如果获取成功，立即执行（即使有其他线程在等待）
3. 如果获取失败，才进入等待队列
4. 允许"插队"行为，提高吞吐量

> 底层都涉及到 `AQS`

## 面试题
1. 为什么会有公平锁/非公平锁的设计？为什么默认非公平锁？

- 恢复挂起的线程到真正锁的获取还是有时间差的，从开发人员来看这个时间微乎其微，但是从CPU的角度来看，这个时间差存在还是很明显的。所以非公平锁能更充分的利用CPU的时间片，尽量减少CPU空间状态时间。
- 使用多线程很重要的考量点是线程切换的开销，当采用非公平锁时，当一个线程请求锁获取同步状态，然后释放同步状态，所以刚释放锁的线程在此刻再次获取同步状态的概率就变得很大，所以就减少了线程的开销。

2. 什么时候用公平锁？什么时候用非公平锁？

- 如果为了更高的吞吐量，很显然非公平锁是比较合适的，因为节省了很多线程切换的时间，吞吐量自然就上去了
- 否则，就用公平锁，公平使用

## 适用场景

### 公平锁适用于：
- 对锁获取顺序有严格要求的场景
- 需要避免线程饥饿的系统
- 对响应时间公平性敏感的应用

### 非公平锁适用于：
- 对整体吞吐量要求较高的场景
- 锁竞争不太激烈的环境
- 可以接受一定不公平性的应用

## 注意事项

1. **性能权衡**：公平锁虽然提供了更好的公平性保证，但会牺牲一定的系统吞吐量
2. **线程安全**：无论使用哪种锁，都需要确保在 `finally` 块中正确释放锁资源
3. **选择建议**：大多数情况下，默认的非公平锁已经足够满足需求
4. **死锁预防**：使用锁时要注意避免死锁情况的发生

## 总结

公平锁和非公平锁是并发编程中的重要概念，它们在保证线程安全的同时，在性能和公平性之间做出了不同的权衡。开发者应根据具体的业务需求和性能要求来选择合适的锁策略。
