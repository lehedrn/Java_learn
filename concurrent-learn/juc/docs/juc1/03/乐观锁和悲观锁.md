# 乐观锁和悲观锁

## 悲观锁 (Pessimistic Locking)

悲观锁是一种保守的并发控制策略，它假设最坏的情况——即认为只要不加锁就一定会发生冲突。

### 特点：
- 在整个数据处理过程中锁定数据
- 阻止其他线程访问被锁定的数据
- 适用于写操作较多的场景
- 实现简单但可能导致性能瓶颈

> `synchronized` 和 `Lock` 的实现类都是悲观锁

### Java中的实现：
```java
// synchronized关键字是典型的悲观锁实现
public synchronized void updateData() {
    // 数据更新逻辑
}

// ReentrantLock也是悲观锁的一种实现
private final ReentrantLock lock = new ReentrantLock();

public void updateWithLock() {
    lock.lock();
    try {
        // 数据更新逻辑
    } finally {
        lock.unlock();
    }
}
```


## 乐观锁 (Optimistic Locking)

乐观锁采用相反的策略，它假设最好的情况——即认为数据一般不会发生冲突。

#### 特点：
- 不会阻塞其他线程的操作
- 在更新时检查数据是否被修改过
- 适用于读操作远多于写操作的场景
- 可能需要重试机制来处理冲突

> 版本号机制和 `CAS` 算法（`Java` 原子类中的递增操作）都是乐观锁的实现方式

### Java中的实现：
```java
// 使用版本号实现乐观锁
public class OptimisticLockExample {
    private int value;
    private int version;
    
    public boolean update(int newValue, int expectedVersion) {
        if (this.version == expectedVersion) {
            this.value = newValue;
            this.version++;
            return true;
        }
        return false; // 更新失败，需要重试
    }
}

// 使用CAS操作实现乐观锁
public class CASLockExample {
    private AtomicInteger atomicValue = new AtomicInteger(0);
    
    public void updateValue() {
        int current;
        do {
            current = atomicValue.get();
        } while (!atomicValue.compareAndSet(current, current + 1));
    }
}
```


## 对比分析

| 特性 | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 冲突假设 | 假设会发生冲突 | 假设不会发生冲突 |
| 加锁时机 | 访问时加锁 | 更新时验证 |
| 并发性能 | 较低 | 较高 |
| 实现复杂度 | 简单 | 复杂 |
| 适用场景 | 写多读少 | 读多写少 |

## 应用场景

#### 悲观锁适用于：
- 数据竞争激烈的环境
- 写操作较多的业务场景
- 对数据一致性要求极高的系统

#### 乐观锁适用于：
- 数据竞争较少的环境
- 读操作远远超过写操作的场景
- 对响应时间要求较高的系统

## 总结

选择乐观锁还是悲观锁主要取决于具体的应用场景。在实际开发中，应该根据系统的并发特点、数据争用情况以及性能要求来合理选择合适的锁策略。
