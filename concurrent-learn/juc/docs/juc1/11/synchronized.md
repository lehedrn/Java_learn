# `synchronized`

## 1. synchronized 的性能变化
`synchronized` 是 Java 中用于控制多线程并发访问共享资源的关键字，它能够保证同一时刻只有一个线程执行某个对象的同步代码块或方法。随着 `JDK` 版本的演进，`synchronized` 的性能也经历了显著优化：

1. **早期版本中的性能问题**
    - 在 JDK 1.5 及更早版本中，`synchronized` 属于重量级锁，每次获取锁都需要向操作系统申请，导致较高的性能开销。

2. **JDK 1.6 后的重要优化**
    - 引入了偏向锁（Biased Locking）、轻量级锁（Lightweight Locking）和自适应自旋等机制，大大提升了 `synchronized` 的性能表现。
    - 偏向锁减少了同一线程多次获取锁的成本；轻量级锁避免了传统重量级锁使用操作系统互斥量产生的开销；自适应自旋则根据前一次在同一锁上的自旋时间及拥有者状态来决定是否继续自旋。

3. **锁升级过程**
    - 无锁 → 偏向锁 → 轻量级锁 → 重量级锁
    - 这个过程是单向的，只能升级不能降级，并且这些优化都是为了减少获得锁和释放锁带来的性能损耗。

4. **现代 `JVM` 对 `synchronized` 的进一步优化**
    - 包括锁粗化（Lock Coarsening）、锁消除（Lock Elimination）等 JIT 编译器层面的技术也被用来提高程序运行效率。

## 2. `synchronized` 锁种类及升级步骤

### 2.1 多线程访问情况

- 只有一个线程来访问，有且唯一
- 有两个线程(两个线程交替访问)
- 竞争激烈，更多线程访问

### 2.2 升级流程

- `synchronized` 用的锁是存在 `Java` 对象头里的 `MarkWord` 中，锁升级功能主要依赖 `MarkWord` 中锁标志位和释放偏向锁标志位
    
    | 锁状态 | 25 位  | 31 位                  | 1 位   | 4bit     | 1bit<br/>偏向锁位 | 2bit<br/>锁标志位 |
    | ------ | ------ | ---------------------- | ------ | -------- |---------------|---------------|
    | 无锁态 | unused | hashCode（如果有调用） | unused | 分代年龄 | 0             | 01            |

    | 锁状态 | 54 位 | 2 位 | 1 位 | 4bit | 1bit<br/>偏向锁位 | 2bit<br/>锁标志位 |
    | ------ | ----- | ---- | ---- | ---- | ------------------ | ------------------ |
    | 偏向锁 | 当前线程指针 Java Thread* | Epoch | unused | 分代年龄 | 1 | 01|

    | 锁状态           | 62 位 | 2bit<br/>锁标志位|
    |---------------| ----- | ------------------ |
    | 轻量级锁 （自旋锁 无锁） | 指向线程栈中 Lock Record 的指针| 00|
    | 重量级锁          | 指向互斥量（重量级锁）的指针 | 10 |
- 锁指向
    - 偏向锁：`MarkWord` 存储的是偏向的线程ID
    - 轻量锁：`MarkWord` 存储的是指向线程栈中 `Lock Record` 的指针
    - 重量锁：`MarkWord` 存储的是指向堆中的 `monitor` 对象 （系统互斥量指针）

### 2.3 无锁

无锁（Lock-Free）是 `synchronized` 锁机制中的初始状态，也是最轻量级的状态。在这个状态下：

- **对象头状态**：对象处于无锁状态时，`MarkWord` 中的偏向锁位为 `0`，锁标志位为 `01`
- **适用场景**：当没有线程竞争，或者对象刚被创建尚未被任何线程锁定时
- **特点**：
    - 不需要任何锁开销，性能最优
    - 可以存储对象的 `hashCode`，只有调用了 `hashCode()` 方法时，对象头中会存储 `hashCode`
    - 当第一个线程访问时，会尝试将锁升级为偏向锁

- 示例
    [SynchronizedUpDemo.java#noLock](../../../src/main/java/com/coderlee/juc1/sync/SynchronizedUpDemo.java)

### 2.4 偏向锁

偏向锁（Biased Locking）是 `synchronized` 锁机制中的一种优化策略，主要针对同一个线程多次获取同一个锁的场景：

- **设计目的**：消除同一数据块在无竞争情况下的同步开销，提高程序性能
- **对象头状态**：
    - 偏向锁位为 `1`
    - 锁标志位为 `01`
    - `MarkWord` 中存储偏向的线程ID（`Java Thread*`）

- **工作原理**：
    - 当第一个线程访问同步代码块时，JVM会将锁偏向该线程
    - 后续该线程再次进入同步代码块时，无需进行任何同步操作
    - 只有当其他线程尝试获取锁时，才会撤销偏向锁

- **适用场景**：
    - 大部分情况下只有一个线程访问同步资源
    - 同一个线程重复获取同一把锁

- **特点**：
    - 减少了同一线程多次获取锁的开销
    - 当出现线程竞争时，需要撤销偏向锁，会有一定的性能损耗
    - 可以通过 `-XX:-UseBiasedLocking` 参数禁用偏向锁，禁用后，默认会直接使用轻量级锁
    - 在JDK 1.6 之后默认是开启偏向锁的，但是启动时间有延迟，默认延迟时间是4秒。需要添加参数 `-XX:+UseBiasedLocking -XX:BiasedLockingStartupDelay=0`，让其在程序启动时立刻启动
    - `Java15` 以后逐步废弃偏向锁，需要手动开启------->维护成本高

- **示例**
  [SynchronizedUpDemo.java#biasedLock](../../../src/main/java/com/coderlee/juc1/sync/SynchronizedUpDemo.java)
- 结论
  - HotSpot的作者经过研究发现，大多数情况下：在多线程情况下，锁不仅不存在多线程竞争，还存在由同一个线程多次获得的情况，偏向锁就是在这种情况下出现的，它的出现是为了解决只有一个线程执行同步时提高性能。
  - 偏向锁会偏向于第一个访问锁的线程，如果在接下来的运行过程中，该锁没有被其他线程访问，则持有偏向锁的线程将永远不需要出发同步。也即偏向锁在资源在没有竞争情况下消除了同步语句，懒得连CAS操作都不做了，直接提高程序性能。
> 注意：偏向锁只有遇到其他线程尝试竞争偏向锁时，持有偏向锁才会释放锁，线程是不会主动释放偏向锁的。

- **偏向锁的撤销**

  - 当有另外一个线程逐步来竞争锁的时候，就不能再使用偏向锁了，要升级为轻量级锁，使用的是等到竞争出现才释放锁的机制
  - 竞争线程尝试CAS更新对象头失败，会等到全局安全点（此时不会执行任何代码）撤销偏向锁，同时检查持有偏向锁的线程是否还在执行：
    - 第一个线程正在执行 `synchronized` 方法（处于同步块），它还没有执行完，其他线程来抢夺，该偏向锁会被取消掉并出现锁升级，此时轻量级锁由原来持有偏向锁的线程持有，继续执行同步代码块，而正在竞争的线程会自动进入自旋等待获得该轻量级锁
    - 第一个线程执行完 `synchronized`（退出同步块），则将对象头设置为无所状态并撤销偏向锁，重新偏向。

### 2.5 轻量级锁
### 2.5 轻量级锁

轻量级锁（Lightweight Locking）是 `synchronized` 锁机制中的中间状态，适用于多个线程交替执行同步代码块的场景：

- **设计目的**：减少无实际竞争情况下的重量级锁开销，提升程序性能
- **对象头状态**：
    - 锁标志位为 `00`
    - `MarkWord` 中存储指向线程栈中 `Lock Record` 的指针

- **工作原理**：
    - 当关闭偏向锁或多个线程交替访问时，对象会升级为轻量级锁
    - 线程在执行同步代码块之前，会在自己的栈帧中创建 `Lock Record`
    - 通过 CAS 操作尝试将对象的 `MarkWord` 更新为指向 `Lock Record` 的指针
    - 如果更新成功，则获取锁成功；如果失败，表示存在竞争，可能需要自旋等待

- **适用场景**：
    - 多个线程交替执行同步代码块（少量竞争）
    - 短时间的同步操作

- **特点**：
    - 相比重量级锁，避免了操作系统的互斥量调用开销
    - 使用自旋方式避免线程阻塞和唤醒的开销
    - 当竞争激烈时会升级为重量级锁
    - 自适应自旋会根据历史自旋情况决定是否继续自旋

- **示例**
  [SynchronizedUpDemo.java#thinLock](../../../src/main/java/com/coderlee/juc1/sync/SynchronizedUpDemo.java)

- 自旋一定程度和次数（Java8 之后是自适应自旋锁------意味着自旋的次数不是固定不变的）：
  - 线程如果自旋成功了，那下次自旋的最大次数会增加，因为JVM认为既然上次成功了，那么这一次也大概率会成功
  - 如果很少会自选成功，那么下次会减少自旋的次数甚至不自旋，避免CPU空转
- 轻量锁和偏向锁的区别：
  - 争夺轻量锁失败时，自旋尝试抢占锁
  - 轻量级锁每次退出同步块都需要释放锁，而偏向锁是在竞争发生时才释放锁

### 2.6 重量级锁

重量级锁（Heavyweight Locking）是 `synchronized` 锁机制中的最终状态，适用于多个线程激烈竞争的场景：

- **设计目的**：处理高并发竞争场景，确保线程安全
- **对象头状态**：
    - 锁标志位为 `10`
    - `MarkWord` 中存储指向堆中 `monitor` 对象的指针（系统互斥量指针）

- **工作原理**：
    - 当轻量级锁竞争失败或自旋次数达到阈值时，锁会升级为重量级锁
    - 线程竞争失败会被挂起，进入阻塞状态
    - 操作系统层面通过互斥量（mutex）实现线程间的同步
    - 持有锁的线程释放锁后，会唤醒等待队列中的线程

- **适用场景**：
    - 多个线程同时竞争同一个锁
    - 同步代码块执行时间较长
    - 线程竞争激烈的场景

- **特点**：
    - 使用操作系统互斥量实现，开销较大
    - 线程阻塞和唤醒需要切换到内核态，消耗较多系统资源
    - 保证了线程间的公平性和正确性
    - 是锁升级的最终形态，无法再降级

- **性能影响**：
    - 线程上下文切换带来较大的性能开销
    - 适用于长时间同步操作或高竞争场景
    - 相比轻量级锁和偏向锁，性能开销最大

### 2.7 小结

#### 2.7.1 锁升级后，hashcode存放在哪儿了

##### 2.7.1.1 **无锁状态（Unlocked）**
- **存储位置**：`MarkWord`
- **说明**：
  - 当对象首次调用 `Object.hashCode()` 方法时，JVM 会计算其一致性哈希码（Identity Hash Code），并将其存储在 `MarkWord` 的 31 位中。
  - 此时 `MarkWord` 中的 `hashCode` 是直接可访问的，且后续调用 `hashCode()` 将返回相同的值。

> “在无锁状态下，Mark Word中可以存储对象的identity hash code值。”

##### 2.7.1.2 **偏向锁状态（Biased Locking）**
- **存储位置**：`ObjectMonitor` 对象
- **说明**：
  - 当对象进入偏向锁状态时，`MarkWord` 被用于存储线程 ID 和 epoch 值，不再能容纳 `hashCode`。
  - 若此时调用 `hashCode()`，JVM 会立即撤销偏向锁，并将对象升级为轻量级锁或重量级锁。
  - 撤销过程中，原来的 `hashCode` 会被保存到 `ObjectMonitor` 类中的字段里，以保证一致性。

> “当一个对象当前正处于偏向锁状态，又收到需要计算其一致性哈希码请求时，它的偏向状态会被立即撤销，并且锁会膨胀为重量级锁。”

##### 2.7.1.3 **轻量级锁状态（Lightweight Locking）**
- **存储位置**：`Lock Record`（线程栈帧中）
- **说明**：
  - JVM 在当前线程的栈帧中创建一个 `Lock Record`，其中包含对原 `MarkWord` 的拷贝。
  - `Lock Record` 可以同时保存 `hashCode` 和 GC 年龄等信息。
  - 因此，在轻量级锁阶段，`hashCode` 可以与锁共存，无需额外迁移。
  - 锁释放后，`hashCode` 会被写回对象头的 `MarkWord` 中。

> “升级为轻量级锁时，JVM会在当前线程的栈帧中创建一个锁记录(Lock Record)空间……可以包含identity hash code。”

##### 2.7.1.4 **重量级锁状态（Heavyweight Locking）**
- **存储位置**：`ObjectMonitor` 对象
- **说明**：
  - 升级为重量级锁后，`MarkWord` 存储的是指向堆中 `monitor` 对象（即 `ObjectMonitor`）的指针。
  - `ObjectMonitor` 内部有专门字段用于记录非加锁状态下的 `MarkWord`，其中包括原始的 `hashCode`。
  - 锁释放后，这些信息会被重新写回到对象头，恢复 `hashCode` 的可访问性。

> “升级为重量级锁后，Mark Word保存的重量级锁指针，代表重量级锁的ObjectMonitor类里有字段记录非加锁状态下的Mark Word。”

##### 2.7.1.5 总结：`hashCode` 的生命周期与存储迁移路径

| 锁状态       | `hashCode` 存储位置               | 是否可变 |
|--------------|-----------------------------------|----------|
| 无锁         | `MarkWord`                        | 否       |
| 偏向锁       | 暂时不可存 → 触发撤销并升级        | 否       |
| 轻量级锁     | `Lock Record`（线程栈帧）          | 否       |
| 重量级锁     | `ObjectMonitor` 内部字段           | 否       |

> **关键结论**：
> - `hashCode` 的值一旦计算，必须保持不变（Java 规范要求）。
> - 所有锁升级操作都会确保 `hashCode` 不丢失，而是通过 `ObjectMonitor` 或 `Lock Record` 进行安全转移。
> - 最终在锁释放时，`hashCode` 会重新写回 `MarkWord`，保证对象的一致性。

##### 补充说明
- 如果一个对象已经调用过 `hashCode()`，则无法再进入偏向锁状态（避免 `hashCode` 被线程 ID 覆盖导致不一致）。
- `ObjectMonitor` 是 HotSpot VM 中管理同步的核心结构，它不仅维护锁状态，还负责保存 `hashCode`、GC 年龄等元数据。

#### 2.7.2 各种锁的优缺点、`synchronized` 锁升级和实现原理

##### 2.7.2.1 **各种锁的优缺点**

| 锁类型       | 优点                                                                 | 缺点                                                                 |
|--------------|----------------------------------------------------------------------|----------------------------------------------------------------------|
| **无锁**     | 性能最优，无任何开销                                                 | 仅适用于无竞争场景                                                   |
| **偏向锁**   | 减少同一线程多次获取锁的开销，提升单线程性能                         | 竞争出现时需撤销锁，存在额外开销；JDK 15+ 已逐步废弃                 |
| **轻量级锁** | 避免操作系统互斥量调用，使用自旋减少上下文切换，适合低竞争场景       | 自旋消耗 CPU 资源；竞争激烈时会升级为重量级锁                        |
| **重量级锁** | 确保高并发下的线程安全，支持公平性和阻塞等待                         | 开销大，涉及内核态切换，性能较低                                   |

##### 2.7.2.2 **`synchronized` 锁升级过程**

`synchronized` 的锁升级是一个单向不可逆的过程：

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
```

- 一句话总结：先自旋，不行再阻塞
- **无锁 → 偏向锁**：当第一个线程访问同步代码块时，`JVM` 将锁偏向该线程。
- **偏向锁 → 轻量级锁**：当其他线程尝试竞争锁时，偏向锁被撤销，升级为轻量级锁。
- **轻量级锁 → 重量级锁**：当自旋失败或竞争激烈时，锁升级为重量级锁，线程进入阻塞状态。

> 升级触发条件：
> - 偏向锁：多个线程竞争
> - 轻量级锁：自旋失败或达到自旋次数上限
> - 重量级锁：长时间持有锁或线程阻塞

##### 2.7.2.3 **`synchronized` 实现原理**

`synchronized` 的底层实现依赖于 `Java` 对象头中的 `MarkWord` 字段：

- **`MarkWord` 结构**：
  - 存储对象的哈希码、GC 年龄、锁状态等元信息
  - 在不同锁状态下，其内容动态变化

- **关键机制**：
  - **CAS 操作**：用于原子更新 `MarkWord`，确保锁获取的安全性
  - **自适应自旋**：根据历史自旋成功率动态调整自旋次数
  - **全局安全点**：在撤销偏向锁时，JVM 会在全局安全点暂停所有线程，保证一致性

##### 2.7.2.4 **锁升级的优化策略**

- **锁粗化（Lock Coarsening）**：
  - JVM 会将相邻的多个同步代码块合并为一个，减少锁的获取和释放次数
  - 提升性能，避免频繁加锁解锁

- **锁消除（Lock Elimination）**：
  - JIT 编译器在运行时分析对象是否为局部变量且不会逃逸，若确认无竞争，则直接移除锁
  - 例如：字符串拼接中 `StringBuilder` 的内部同步可被消除

- **偏向锁延迟启用**：
  - JDK 默认延迟 4 秒启用偏向锁，避免启动阶段频繁竞争导致性能下降
  - 可通过 `-XX:BiasedLockingStartupDelay=0` 禁用延迟

##### 2.7.2.5 **实际应用建议**

- **单线程场景**：优先使用偏向锁，提升性能
- **多线程交替访问**：适合轻量级锁，避免阻塞
- **高竞争场景**：使用重量级锁，确保正确性
- **避免频繁锁竞争**：合理设计业务逻辑，减少锁粒度


> 注意：
> - `synchronized` 是 JVM 层面的原生锁，无需手动管理
> - 锁升级过程由 JVM 自动完成，开发者无需干预
> - JDK 15+ 中偏向锁已逐步废弃


## 3. JIT编译器对锁的优化

### 3.1 JIT介绍

JIT（Just-In-Time）编译器是 Java 虚拟机（JVM）中的关键组件，负责将字节码（Bytecode）在运行时动态编译为本地机器码，以提升程序执行效率。JIT 编译器通过分析热点代码（Hot Spot），对频繁执行的代码进行优化，从而显著提高性能。

- **主要功能**：
  - **热点代码识别**：通过计数器统计方法或代码块的执行频率，识别出“热点”区域。
  - **即时编译**：将热点代码编译为本地机器指令，减少解释执行的开销。
  - **优化策略**：包括内联、逃逸分析、锁消除、锁粗化等。

- **优势**：
  - 提升程序运行速度
  - 减少内存占用
  - 支持运行时优化，适应不同场景

### 3.2 锁消除

锁消除（Lock Elimination）是 JIT 编译器的一种优化技术，用于在运行时检测到某个对象不会被多个线程共享时，自动移除对该对象的同步操作。

- **实现原理**：
  - 利用**逃逸分析**（Escape Analysis）判断对象是否“逃逸”出当前方法或线程作用域。
  - 如果对象仅在当前方法内部使用，且不会被其他线程访问，则 JVM 可安全地移除其上的 `synchronized` 锁。

- **示例**：
[LockClearDemo.java](../../../src/main/java/com/coderlee/juc1/sync/LockClearDemo.java)
- 在上述代码中，`StringBuilder` 是局部变量，不会逃逸到外部，JIT 编译器会判断无需加锁，直接移除 `synchronized` 块。

- **优点**：
  - 减少不必要的锁开销
  - 提高并发性能
  - 自动完成，无需开发者干预

- **触发条件**：
  - 对象为局部变量
  - 不会被返回给调用者
  - 不会被传递给其他线程

> 注意：锁消除依赖于逃逸分析，若对象可能被逃逸，则不会进行优化。

### 3.3 锁粗化

锁粗化（Lock Coarsening）是 JIT 编译器的另一种优化策略，旨在减少频繁的锁获取和释放操作，提升性能。

- **实现原理**：
  - 当发现多个连续的同步代码块操作的是同一个对象时，JVM 会将这些代码块合并为一个更大的同步块，从而减少锁的获取和释放次数。

- **示例**：
[LockBigDemo.java](../../../src/main/java/com/coderlee/juc1/sync/LockBigDemo.java)

- **优点**：
  - 减少锁的获取和释放次数
  - 降低上下文切换开销
  - 提高整体执行效率

- **适用场景**：
  - 多个相邻的同步代码块操作同一对象
  - 同步粒度较细，但逻辑上可合并

> 小结：锁粗化通过合并多个小范围的同步操作，减少了锁的频繁切换，提升了性能。

---

### 3.4 总结

| 优化类型   | 作用                           | 实现方式               | 适用场景                     |
|------------|--------------------------------|------------------------|------------------------------|
| 锁消除     | 移除不必要的锁                 | 逃逸分析               | 局部变量、不共享对象         |
| 锁粗化     | 合并多个同步块，减少锁操作     | 代码块合并             | 相邻同步块操作同一对象       |

> 提示：JIT 编译器的这些优化都是自动进行的，开发者无需手动干预，但理解其原理有助于编写更高效的并发代码。
