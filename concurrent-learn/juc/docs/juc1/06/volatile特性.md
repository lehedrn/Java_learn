# `volatile` 特性

## 保证可见性

`volatile` 关键字通过内存屏障机制确保变量修改对所有线程的可见性：
- 写屏障：当线程写入 `volatile` 变量时，会在写操作后插入写内存屏障，强制将工作内存中变量的最新值刷新到主内存
- 读屏障：当线程读取 `volatile` 变量时，会在读操作前插入读内存屏障，强制从主内存中获取变量的最新值

Java内存模型为了保证数据访问的原子性、可见性和有序性，定义了以下8个基本操作：

1. **read(读取)**: 从主内存传输变量值到线程的工作内存
2. **load(载入)**: 将read操作从主内存得到的变量值放入工作内存的变量副本中
3. **use(使用)**: 把工作内存中的变量值传递给执行引擎，每当虚拟机遇到需要使用变量值的字节码指令时都会执行这个操作
4. **assign(赋值)**: 把从执行引擎接收到的值赋给工作内存中的变量，每当虚拟机遇到给变量赋值的字节码指令时都会执行这个操作
5. **store(存储)**: 把工作内存中的变量值传送到主内存中，以便随后的write操作使用
6. **write(写入)**: 把store操作从工作内存得到的变量值放入主内存的变量中
7. **lock(锁定)**: 作用于主内存中的变量，标识该变量被某个线程独占
8. **unlock(解锁)**: 作用于主内存中的变量，释放被锁定的变量

这些操作必须满足一定的规则，例如：
- read和load、store和write必须成对出现
- 不允许一个线程丢弃最近的assign操作
- 一个新的变量只能在主内存中诞生
- volatile变量还有一些特殊的语义约束

这些底层机制是实现`volatile`关键字可见性、原子性和有序性特性的基础。


## 没有原子性

- 对于 `voaltile` 变量具备可见性，JVM只是保证从主内存加载到线程工作内存的值是最新的，也仅仅是数据加载时是最新的。但是多线程环境下，“数据计算”和“数据赋值”操作可能多次出现，若数据在加载之后，若主内存 `volatile` 修饰变量发生修改之后，线程工作内存的操作将会作废去读主内存最新值，操作出现写丢失问题。即各线程私有内存和主内存公共内存中变量不同步，进而导致数据不一致。由此可见 `volatile` 解决的是变量读时的可见性问题，但无法保证原子性，对于多线程修改主内存共享变量的场景必须加锁同步。
- 至于怎么去理解这个写丢失的问题，就是再将数据读取到本地内存到写回主内存中有三个步骤：数据加载---->数据计算---->数据赋值，如果第二个线程在第一个线程读取旧值与写回新值期间读取共享变量的值，那么第二个线程将会与第一个线程一起看到同一个值，并执行自己的操作，一旦其中一个线程对 `volatile` 修饰的变量先行完成操作刷回主内存后，另一个线程会作废自己的操作，然后重新去读取最新的值再进行操作，这样的话，它自身的那一次操作就丢失了，这就造成了线程安全失败，因此，这个问题需要使用 `synchronized` 修饰以保证线程安全性。
- 结论：`volatile` 变量不适合参与到依赖当前值的运算，如 `i++`，`i=i+1` 之类的，通常用来保存某个状态的 `boolean` 值或者 `int` 值，也正是由于 `volatile` 变量只能保证可见性，在不符合以下规则的运算场景中，我们仍然要通过加锁来保证原子性：
  - 运算结果并不依赖变量的当前值，或者能够确保只有单一的线程修改变量的值
  - 变量不需要与其他的状态变量共同参与不变约束
- 面试回答为什么不具备原子性：举例 `i++` 的例子，在字节码文件中，`i++` 分为三部，间隙期间不同步非原子操作
  - 对于 `volatile` 变量，JVM只是保证从主内存加载到线程工作内存的值是最新的，也就是数据加载时是最新的，如果第二个线程在第一个线程读取旧值和写回新值期间读取i的域值，也就造成了线程安全问题。

## 有序性（指令禁重排） 

- 在每一个 `volatile` 写操作前面插入一个 `StoreStore` 屏障 ---> `StoreStore` 屏障可以保证在 `volatile` 写之前，其前面所有的普通写操作都已经刷新到主内存中。
- 在每一个 `volatile` 写操作后面插入一个 `StoreLoad` 屏障 ---> `StoreLoad` 屏障的作用是避免 `volatile` 写与后面可能有的 `volatile` 读/写操作重排序
- 在每一个 `volatile` 读操作后面插入一个 `LoadLoad` 屏障 ---> `LoadLoad` 屏障用来禁止处理器把上面的 `volatile` 读与下面的普通读重排序
- 在每一个 `volatile` 读操作后面插入一个 `LoadStore` 屏障 ---> `LoadStore` 屏障用来禁止处理器把上面的 `volatile` 读与下面的普通写重排序

### 案例说明

**代码示例**
```
public class VolatileTest {
int i = 0;
volatile boolean flag = false;

    public void write(){
        i = 2;           // 普通写操作
        flag = true;     // volatile写操作
    }
    
    public void read(){
        if(flag){
            System.out.println("---i = " + i);
        }
    }
}
```

#### volatile 有序性保障分析

基于提供的示例代码 `VolatileTest`，我们可以看到 `volatile` 变量 `flag` 的读写操作如何通过插入内存屏障来保证指令的有序性。

##### 写操作中的屏障

在 `write()` 方法中：
```java
public void write(){
    i = 2;           // 普通写操作
    flag = true;     // volatile写操作
}
```

JVM会在 `flag = true` 这个 `volatile` 写操作前后插入内存屏障：

1. **StoreStore屏障**：在 `i = 2` 和 `flag = true` 之间隐式存在，确保普通的写操作（`i = 2`）在 `volatile` 写（`flag = true`）之前完成并刷新到主内存。
2. **StoreLoad屏障**：在 `flag = true` 之后插入，防止 `volatile` 写操作与后续可能的 `volatile` 读/写操作发生重排序。

##### 读操作中的屏障

在 `read()` 方法中：
```java
public void read(){
    if(flag){  // volatile读操作
        System.out.println("---i = " + i);
    }
}
```

JVM会在 `if(flag)` 这个 `volatile` 读操作后插入内存屏障：

1. **LoadLoad屏障**：在 `flag` 读取后插入，防止上面的 `volatile` 读与下面的普通读（`i`) 的读取）重排序。
2. **LoadStore屏障**：也在 `flag` 读取后插入，防止上面的 `volatile` 读与下面的普通写操作重排序。

这样通过内存屏障的插入，`volatile` 变量保证了：
- 在写入 `volatile` 变量之前的所有写操作都已完成并刷新到主内存
- 在读取 `volatile` 变量之后的所有读写操作都不会被重排序到 `volatile` 读之前
- 多线程环境下能够观察到一致的执行顺序，从而保证了程序的有序性
