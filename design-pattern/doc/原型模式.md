# 原型模式

## 概述

原型模式（Prototype Pattern）属于创建型设计模式。它通过复制（克隆）现有的实例来创建新的对象，而不是通过传统的 new 关键字来创建。原型模式的核心思想是利用一个已经存在的实例作为原型，通过复制它来创建新的对象，这样可以避免重复的初始化过程，提高性能。

### 核心要素
1. **原型接口（Prototype）**：声明克隆方法的接口
2. **具体原型类（Concrete Prototype）**：实现克隆方法的具体类
3. **客户类（Client）**：使用原型接口的类，通过克隆原型创建新对象

### 主要优势
- ✅ **性能优化**：直接复制内存中的对象，避免复杂的初始化过程
- ✅ **简化创建**：无需重新初始化，保留原型对象的状态
- ✅ **动态配置**：可以在运行时通过修改原型状态来影响克隆结果
- ✅ **减少耦合**：客户端无需知道具体产品类的类名

## 浅拷贝与深拷贝

原型模式的核心是理解浅拷贝和深拷贝的区别，这是正确使用原型模式的关键。

### 浅拷贝（Shallow Copy）

#### 概念
浅拷贝创建一个新对象，但对象内部的引用类型字段仍然指向原来的对象。也就是说，只复制基本类型字段，对于引用类型字段只复制引用地址。

#### 特点
- ✅ **复制速度快**：只需复制引用地址
- ✅ **内存占用少**：多个对象共享引用类型字段
- ❌ **数据不独立**：修改一个对象的引用类型字段会影响其他对象
- ❌ **安全性低**：存在数据污染的风险

#### 代码示例
📄 [`Monster.java - 浅拷贝实现`](../src/main/java/com/coderlee/designpattern/creational/prototype/Monster.java#L18-L30)
#### 适用场景
- 引用类型字段是不可变对象（如 `String`）
- 确定不会修改引用类型字段
- 追求性能且能接受共享数据

---

### 深拷贝（Deep Copy）

#### 概念
深拷贝创建一个完全独立的新对象，包括对象内部的所有引用类型字段也会被递归复制。修改深拷贝后的对象不会影响到原始对象。

#### 特点
- ✅ **数据完全独立**：修改新对象不影响原对象
- ✅ **安全性高**：不存在数据共享问题
- ❌ **复制速度慢**：需要递归复制所有引用对象
- ❌ **内存占用多**：每个对象都有独立的副本

#### 代码示例
📄 [`Monster.java - 深拷贝实现`](../src/main/java/com/coderlee/designpattern/creational/prototype/Monster.java#L24-L29)
#### 适用场景
- 需要完全独立的对象副本
- 引用类型字段是可变的
- 修改对象时不能影响其他对象
- 生产环境推荐使用

---

### 浅拷贝 vs 深拷贝对比

| 对比维度 | 浅拷贝 | 深拷贝 |
|---------|--------|--------|
| **复制速度** | ⭐⭐⭐⭐⭐ 快 | ⭐⭐⭐ 慢 |
| **内存占用** | ⭐⭐⭐⭐⭐ 少 | ⭐⭐⭐ 多 |
| **数据独立性** | ❌ 不独立 | ✅ 完全独立 |
| **安全性** | ⭐⭐ 低 | ⭐⭐⭐⭐⭐ 高 |
| **修改影响** | 会影响其他对象 | 不影响其他对象 |
| **适用场景** | 只读或不可变对象 | 需要修改的可变对象 |
| **推荐度** | ⭐⭐ 谨慎使用 | ⭐⭐⭐⭐⭐ 推荐使用 |

## 优缺点分析

### ✅ 优点

1. **性能优秀**
   - 直接复制内存中的对象，避免复杂的初始化过程
   - 特别是当对象创建成本较高时，优势明显

2. **简化对象创建**
   - 无需重新初始化，保留原型对象的状态
   - 可以动态地增加和删除原型

3. **降低耦合度**
   - 客户端无需知道具体产品类的类名
   - 只需要知道原型接口即可

4. **支持动态配置**
   - 可以在运行时通过修改原型状态来影响克隆结果
   - 支持产品族的灵活配置

5. **便于批量生成**
   - 适合批量生成具有相同基础属性的对象
   - 通过配置实现差异化

### ❌ 缺点

1. **深拷贝实现复杂**
   - 需要为每个类实现克隆方法
   - 对于复杂的对象结构，深拷贝代码量大

2. **内存占用增加**
   - 每个克隆对象都需要独立的内存空间
   - 深拷贝会复制整个对象图

3. **循环引用问题**
   - 如果对象之间存在循环引用，深拷贝可能陷入死循环
   - 需要特殊处理循环引用

4. **Cloneable 接口限制**
   - Java 的 Cloneable 接口设计存在缺陷
   - protected 的 clone() 方法访问受限

5. **浅拷贝的风险**
   - 如果不理解浅拷贝和深拷贝的区别，可能导致数据污染
   - 共享引用类型字段可能引发意外问题

## 适用场景

### ✅ 适合使用的情况

1. **对象创建成本高**
   - 初始化过程复杂、耗时
   - 需要大量资源才能创建的对象

2. **批量生成相似对象**
   - 游戏开发中的怪物、道具生成
   - UI 界面中的控件复制
   - 文档编辑中的图形复制

3. **保护性复制**
   - 需要保存对象的当前状态
   - 支持撤销/重做功能

4. **动态配置场景**
   - 需要在运行时动态添加/删除产品
   - 产品种类不固定的情况

5. **缓存对象池**
   - 配合享元模式使用
   - 提高对象复用率

### ❌ 不适合使用的情况

1. **对象创建简单**
   - 直接使用 new 关键字更简洁
   - 不需要额外的复杂度

2. **对象内部有唯一标识**
   - 如数据库 ID、UUID 等唯一字段
   - 克隆后需要手动修改这些字段

3. **存在循环引用**
   - 对象之间形成循环依赖
   - 深拷贝难以正确处理

4. **包含不可克隆的字段**
   - 如文件句柄、网络连接等资源
   - 这些字段无法或不应被复制

5. **对内存要求极高**
   - 内存资源极其有限的嵌入式系统
   - 需要严格控制内存占用的场景

## 与其他创建型模式的对比

### 原型模式 vs 工厂方法模式

| 对比维度 | 原型模式 | 工厂方法模式 |
|---------|---------|------------|
| **创建方式** | 复制现有对象 | 通过工厂方法 new 对象 |
| **性能** | ⭐⭐⭐⭐⭐ 高 | ⭐⭐⭐ 中 |
| **复杂度** | ⭐⭐⭐ 中 | ⭐⭐⭐⭐ 较高 |
| **适用场景** | 对象创建成本高 | 对象创建逻辑复杂 |
| **代码量** | 较少 | 较多 |
| **灵活性** | 高，可动态添加原型 | 较低，需修改工厂类 |

### 原型模式 vs 建造者模式

| 对比维度 | 原型模式 | 建造者模式 |
|---------|---------|-----------|
| **关注点** | 快速复制对象 | 逐步构建复杂对象 |
| **创建过程** | 一次性克隆 | 分步骤构建 |
| **适用对象** | 已有对象复制 | 复杂对象创建 |
| **灵活性** | 保留原型状态 | 可灵活组合部件 |

### 原型模式 vs 单例模式

| 对比维度 | 原型模式 | 单例模式 |
|---------|---------|---------|
| **实例数量** | 多个实例 | 唯一实例 |
| **目的** | 创建新对象 | 控制实例数量 |
| **关系** | 可以结合使用 | 可以结合使用 |

## 常见问题

### Q1: 为什么不使用 Java 自带的 Cloneable 接口？

**答：** Java 的 Cloneable 接口存在以下问题：
1. clone() 方法是 protected 的，访问受限
2. 必须重写 clone() 方法才能实现真正的深拷贝
3. 容易忘记处理引用类型字段的深拷贝
4. 异常处理复杂（CloneNotSupportedException）

**本实现的替代方案：**
- 自定义 Prototype 接口，明确深浅拷贝
- 使用拷贝构造方法，语义更清晰
- 避免异常处理的复杂性

### Q2: 浅拷贝和深拷贝应该如何选择？

**答：** 选择原则：
1. **默认使用深拷贝**：保证数据独立性
2. **以下情况可使用浅拷贝**：
   - 引用类型字段是不可变对象（String、Integer 等）
   - 确定不会修改引用类型字段
   - 追求极致性能且能接受共享数据

### Q3: 如何处理对象图中的循环引用？

**答：** 循环引用的解决方案：
1. 使用 visited 集合记录已访问的对象
2. 在深拷贝前检查是否已访问过
3. 如果已访问，直接返回之前创建的副本

### Q4: 原型模式与序列化的区别？

**答：** 两者都可以实现对象复制，但有区别：

| 对比维度 | 原型模式 | 序列化 |
|---------|---------|-------|
| **性能** | ⭐⭐⭐⭐⭐ 高 | ⭐⭐ 低 |
| **实现复杂度** | 中等 | 简单 |
| **适用场景** | 频繁复制 | 偶尔复制 |
| **额外依赖** | 无 | 需要 Serializable |

## 总结

### 核心要点

🎯 **核心价值**：通过复制现有对象来创建新对象，提高性能  
📦 **关键实现**：明确区分浅拷贝和深拷贝  
✅ **最佳实践**：优先使用深拷贝，保证数据独立性  
🔧 **使用技巧**：配合注册表模式，降低耦合度
