# 建造者模式

## 概述

**建造者模式（Builder Pattern）** 是一种创建型设计模式，用于将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。

### 核心思想
- 分步骤构建一个复杂对象
- 将构建过程封装在独立的对象中
- 允许通过相同的构建过程创建不同的产品

### 适用场景
1. **复杂对象的创建**：当创建复杂对象的算法应该独立于该对象的组成部分以及它们的装配方式时
2. **不同的表示**：当构造过程必须允许被构造的对象有不同的表示时
3. **构建顺序控制**：当需要控制创建对象的步骤顺序时
4. **参数化配置**：当对象的创建需要多个参数，其中一些是可选的时候

## 经典建造者模式

### 结构组成

经典建造者模式包含以下 4 个核心角色：

```

┌─────────────────────────────────────────────────┐
│  1. Product（产品）                              │
│     - 要创建的复杂对象                            │
│     - Computer.java                             │
└─────────────────────────────────────────────────┘
▲
│ 创建
┌─────────────────────────────────────────────────┐
│  2. Builder（抽象建造者）                         │
│     - 定义创建产品的各个部件的接口                  │
│     - ComputerBuilder.java                      │
└─────────────────────────────────────────────────┘
▲                    ▲
│ 实现                │ 实现
┌──────────────┐    ┌──────────────┐
│ GamingBuilder│    │ OfficeBuilder│
│ （游戏电脑）  │    │ （办公电脑）  │
└──────────────┘    └──────────────┘
│                   │
└─────────┬─────────┘
│ 使用
┌─────────────────┐
│  3. Director    │
│  （指挥者）      │
│  ComputerDirector│
└─────────────────┘
│ 控制
┌─────────────────┐
│  4. Client      │
│  （客户端）      │
└─────────────────┘
```
### 各角色职责

#### 1. Product（产品角色）
📄 [`Computer.java`](../src/main/java/com/coderlee/designpattern/creational/builder/classics/Computer.java)

**职责：** 要创建的复杂对象——电脑

**核心特点：**
- 包含多个组成部分：CPU、主板、内存、显卡、存储器、电源
- 各部分相对独立，通过 setter 方法逐步设置
- 提供 `toString()` 方法方便查看完整配置

#### 2. Builder（抽象建造者）
📄 [`ComputerBuilder.java`](../src/main/java/com/coderlee/designpattern/creational/builder/classics/ComputerBuilder.java)

**职责：** 定义创建产品各个部件的标准接口

**核心特点：**
- 定义了 6 个构建步骤：`buildCpu()`、`buildMainBoard()`、`buildRam()`、`buildGpu()`、`buildStorage()`、`buildPower()`
- 提供 `getResult()` 方法获取最终产品
- 不涉及具体实现细节，由具体建造者实现

#### 3. ConcreteBuilder（具体建造者）

##### 📄 [`GamingComputerBuilder.java`](../src/main/java/com/coderlee/designpattern/creational/builder/classics/GamingComputerBuilder.java)

**职责：** 构建高性能游戏电脑

**核心特点：**
- 实现 `ComputerBuilder` 接口
- 维护一个 `Computer` 实例
- 每个构建方法设置高端游戏配件
- 返回完整的游戏电脑产品

**典型配置：** Intel Core i9-13900K + RTX 4090 + 32GB DDR5

##### 📄 [`OfficeComputerBuilder.java`](../src/main/java/com/coderlee/designpattern/creational/builder/classics/OfficeComputerBuilder.java)

**职责：** 构建实用型办公电脑

**核心特点：**
- 实现 `ComputerBuilder` 接口
- 维护一个 `Computer` 实例
- 每个构建方法设置实用办公配件
- 注重性价比和低功耗

**典型配置：** Intel Core i5-12400 + 集成显卡 + 16GB DDR4

#### 4. Director（指挥者）
📄 [`ComputerDirector.java`](../src/main/java/com/coderlee/designpattern/creational/builder/classics/ComputerDirector.java)

**职责：** 控制构建流程的执行顺序

**核心特点：**
- 持有 `ComputerBuilder` 的引用
- 按照固定顺序调用各个构建方法
- 提供 `setBuilder()` 方法设置建造者
- 提供 `getComputer()` 方法获取最终产品
- 进行空值检查，确保安全性

**构建流程：** CPU → 主板 → 内存 → 显卡 → 存储器 → 电源

#### 5. Client（客户端）
📄 [`Client.java`](../src/main/java/com/coderlee/designpattern/creational/builder/classics/Client.java)

**职责：** 演示建造者模式的完整使用流程

**使用步骤：**
1. 创建 `ComputerDirector` 指挥者
2. 创建具体建造者（如 `GamingComputerBuilder`）
3. 将建造者设置到指挥者中
4. 调用 `constructComputer()` 构建产品
5. 通过 `getComputer()` 获取最终产品

### 经典版时序图

### 优缺点分析

#### ✅ 优点

1. **封装性好**：客户端不需要知道产品内部组成细节
2. **便于解耦**：构建代码与表示代码分离
3. **易于扩展**：新增一个具体建造者无需修改现有代码（符合 OCP）
4. **控制构建过程**：Director 可以精确控制构建顺序和质量检查
5. **复用性高**：同样的构建过程可以用于不同的产品

#### ❌ 缺点

1. **增加类的数量**：每个产品都需要一个具体建造者
2. **适用范围有限**：要求产品具有共同点
3. **灵活性不足**：构建过程由 Director 固定，难以应对频繁变化

## 简化版建造者模式

### 结构组成

简化版建造者模式将 Builder 作为内部静态类，无需 Director 角色：

```

┌─────────────────────────────────────────────────┐
│  Product（产品）                                 │
│  Computer.java（包含静态内部 Builder 类）         │
│                                                  │
│  ┌─────────────────────────────────┐            │
│  │  Static Inner Builder Class     │            │
│  │  - 必选参数（构造函数传入）      │            │
│  │  - 可选参数（默认值 + setter）   │            │
│  │  - 链式调用（返回 this）         │            │
│  │  - build() 方法                  │            │
│  └─────────────────────────────────┘            │
└─────────────────────────────────────────────────┘
▲
│ 直接使用
┌─────────────────┐
│  Client         │
│  （客户端）      │
└─────────────────┘
```
### 核心实现

#### Product（产品类）
📄 [`Computer.java`](../src/main/java/com/coderlee/designpattern/creational/builder/simple/Computer.java)

**核心特点：**
1. **不可变对象**：所有字段都是 `final`，保证不可变性
2. **私有构造函数**：防止外部直接 `new`，必须通过 Builder 创建
3. **参数分类管理**：
   - **必选参数**：`cpu`、`mainboard`（通过构造函数强制传入）
   - **可选参数**：`ram`、`gpu`、`storage`、`power`（有合理默认值）

**内部 Builder 类设计要点：**
- 构造函数强制传入必选参数
- 可选参数提供默认值
- 每个 setter 方法返回 `this`，支持链式调用
- `build()` 方法创建最终的 Computer 对象

#### Client（客户端）
📄 [`Client.java`](../src/main/java/com/coderlee/designpattern/creational/builder/simple/Client.java)

**两种典型使用场景：**

##### 场景一：自定义配置（链式调用）
构建高性能游戏电脑，所有参数都自定义配置

##### 场景二：使用默认配置（只传必选参数）
构建办公电脑，仅传入必选参数，其他使用默认值

### 简化版时序图

```

Client                    Computer.Builder              Computer
│                             │                            │
│  new Builder(cpu, board)    │                            │
├────────────────────────────>│                            │
│                             │                            │
│  ram("32GB")                │                            │
├────────────────────────────>│                            │
│  (return this)              │                            │
│<────────────────────────────┤                            │
│                             │                            │
│  gpu("RTX4090")             │                            │
├────────────────────────────>│                            │
│  (return this)              │                            │
│<────────────────────────────┤                            │
│                             │                            │
│  build()                    │                            │
├────────────────────────────>│                            │
│                             │  new Computer(this)        │
│                             ├───────────────────────────>│
│  Computer                   │                            │
│<────────────────────────────┤                            │
│                             │                            │
```
### 优缺点分析

#### ✅ 优点

1. **代码简洁**：无需单独的 Builder 接口和 Director 类
2. **链式调用**：Fluent API，代码优雅流畅
3. **参数管理灵活**：区分必选/可选参数，有默认值
4. **不可变对象**：线程安全，状态一致性
5. **类型安全**：编译期检查必选参数

#### ❌ 缺点

1. **无法控制构建顺序**：调用顺序完全自由
2. **不适合复杂构建逻辑**：没有 Director 控制流程
3. **Builder 类膨胀**：所有 setter 都在一个类中

## 经典版 vs 简化版

### 对比表格

| 特性 | 经典建造者模式 | 简化建造者模式 |
|------|----------------|----------------|
| **Builder 结构** | 独立接口 + 实现类 | 内部静态类 |
| **是否需要 Director** | ✅ 需要 | ❌ 不需要 |
| **代码复杂度** | 较高（5+ 个类） | 较低（1 个类） |
| **构建流程控制** | Director 严格控制 | 自由调用 |
| **参数管理** | 所有参数平等对待 | 区分必选/可选 |
| **链式调用** | ❌ 不支持 | ✅ 支持 |
| **不可变对象** | ❌ 通常可变 | ✅ 不可变 |
| **适用场景** | 复杂构建流程 | 参数组合灵活 |
| **扩展性** | 容易扩展新建造者 | 需要修改原类 |
| **代码量** | 多 | 少 |

### 选择建议

#### 🎯 选择经典版的场景：
- 构建流程复杂，需要严格控制每一步的顺序
- 需要质量检查，构建过程中需要验证中间结果
- 多种构建流程，不同的 Director 控制不同流程
- 产品差异大，不同产品的构建逻辑完全不同

**典型案例：** 建筑房屋、组装机器、制作套餐

#### 🎯 选择简化版的场景：
- 参数较多，对象有很多可配置项
- 参数可选，很多参数有合理默认值
- 灵活性高，希望自由组合参数
- 代码简洁，不想写太多类
- 不可变需求，需要线程安全的对象

**典型案例：** HTTP 请求、数据库查询、测试数据、配置对象

## 最佳实践

### 1. 何时使用建造者模式

✅ **推荐使用：**
- 创建复杂对象，需要多个步骤
- 对象有很多配置参数（尤其是可选参数）
- 需要控制对象的创建过程
- 希望创建不可变对象
- 参数的含义不明显，容易传错

❌ **不推荐：**
- 对象很简单，几个参数就能创建
- 所有参数都是必需的，且含义明确
- 对象需要频繁修改（可变对象）
- 过度设计

### 2. 设计原则

- **区分必选参数和可选参数**：必选参数通过构造函数强制传入
- **参数验证**：在 `build()` 方法中进行必要的参数校验
- **链式调用的流畅性**：保持方法命名一致性
- **防御性编程**：对可变参数进行防御性拷贝或使用 `Objects.requireNonNullElse`

### 3. Lombok @Builder 注解

使用 Lombok 可以进一步简化代码，但注意所有参数都是可选的，无法强制必选参数。

## 总结

### 核心要点

1. **建造者模式的本质**：分步骤构建复杂对象，将构建与表示分离

2. **两种实现方式**：
   - **经典版**：适合复杂流程，需要 Director 控制（5 个类）
   - **简化版**：适合参数配置，链式调用更优雅（1 个类）

3. **关键优势**：
   - 封装复杂对象的创建过程
   - 支持不同的产品表示
   - 可以创建不可变对象
   - 代码更易读和维护

### 记忆口诀

> **建造者，分步骤，复杂对象轻松造；**  
> **经典版，有导演，流程控制很规范；**  
> **简化版，链式调，参数配置真方便；**  
> **必选参，不能少，可选参，有默认；**  
> **不可变，线程安，代码优雅又安全！**
