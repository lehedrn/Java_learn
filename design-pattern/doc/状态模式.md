# 状态模式（State Pattern）

## 一、概述

**状态模式**是一种行为型设计模式，它允许一个对象在其内部状态改变时改变它的行为。该模式将状态封装成独立的类，并将上下文的请求委托给当前状态对象处理。

### 1.1 核心思想

- 将与特定状态相关的行为局部化
- 将不同状态的行为分割到不同的类中
- 避免使用大量的条件语句（if/else 或 switch）来判断当前状态
- 状态转换逻辑清晰，易于维护

### 1.2 解决的问题

在传统编程中，处理状态转换通常会使用大量的条件语句：

```java
// ❌ 传统方式：大量条件语句
public void processOrder(Order order, String action) {
    if (order.getState() == UNPAID) {
        if (action.equals("pay")) {
            // 支付逻辑
            order.setState(PAID);
        } else if (action.equals("cancel")) {
            // 取消逻辑
            order.setState(CANCELLED);
        } else {
            System.out.println("操作不允许");
        }
    } else if (order.getState() == PAID) {
        if (action.equals("ship")) {
            // 发货逻辑
            order.setState(SHIPPED);
        } else if (action.equals("cancel")) {
            System.out.println("需要申请退款");
        }
        // ... 更多条件判断
    }
    // ... 更多状态判断
}
```

使用状态模式后，代码结构更清晰：

```java
// ✅ 状态模式：每个状态类负责自己的行为
public class UnpaidState implements State {
    public void cancel(OrderContext context) {
        context.setState(new CancelledState());
    }
    // 其他操作...
}
```

### 2.1 角色说明

| 角色 | 职责 |
|------|------|
| **State（状态接口）** | 定义所有具体状态类需要实现的行为接口 |
| **ConcreteState（具体状态）** | 实现状态接口，每个类代表一个具体状态，包含该状态下的行为逻辑和状态转换 |
| **Context（上下文）** | 持有当前状态对象的引用，定义客户端需要的接口，将请求委托给当前状态对象处理 |

## 三、代码实现

### 3.1 状态接口

```java
public interface State {
    void pay(OrderContext context);
    void ship(OrderContext context);
    void receive(OrderContext context);
    void cancel(OrderContext context);
    String getName();
}
```

### 3.2 具体状态类（以 UnpaidState 为例）

```java
public class UnpaidState implements State {
    @Override
    public void pay(OrderContext context) {
        System.out.println("订单支付成功");
        context.setState(new PaidState());  // 状态转换
    }

    @Override
    public void ship(OrderContext context) {
        System.out.println("操作失败：订单尚未支付，不能发货");
    }

    @Override
    public void cancel(OrderContext context) {
        System.out.println("订单已取消");
        context.setState(new CancelledState());  // 状态转换
    }

    // ... 其他方法
}
```

### 3.3 上下文类

```java
public class OrderContext {
    private State state;
    private String orderId;

    public OrderContext(String orderId) {
        this.state = new UnpaidState();  // 初始状态
        this.orderId = orderId;
    }

    public void pay() {
        state.pay(this);  // 委托给当前状态处理
    }

    public void setState(State state) {
        this.state = state;  // 状态转换
    }
}
```

## 五、状态模式 vs 策略模式

这两种模式结构相似，但意图不同：

| 对比项 | 状态模式 | 策略模式 |
|--------|----------|----------|
| **意图** | 管理对象的内部状态 | 选择算法或行为 |
| **状态转换** | 状态之间会相互转换 | 策略之间独立，无转换概念 |
| **选择方式** | 状态由上下文自动管理 | 策略由客户端或上下文显式选择 |
| **复用性** | 具体状态通常不复用 | 策略类可在多个上下文中复用 |

## 六、优缺点

### 6.1 优点

1. **消除条件语句**：避免了大量的 if/else 或 switch 语句
2. **单一职责原则**：每个状态类只负责一种状态的行为
3. **开闭原则**：添加新状态只需添加新类，无需修改现有代码
4. **清晰的状态转换**：状态转换逻辑集中在状态类中，易于理解
5. **便于维护**：修改某个状态的行为只需修改对应的状态类

### 6.2 缺点

1. **类数量增加**：每个状态都需要一个类，可能导致类爆炸
2. **状态转换逻辑分散**：复杂的状态转换逻辑可能分散在多个类中
3. **对开闭原则的支持不完全**：添加新的行为需要修改所有状态类

## 七、适用场景

1. **对象行为依赖于状态**：一个对象的行为取决于它的状态，并且必须在运行时根据状态改变行为
2. **大量条件语句**：代码中包含大量与状态相关的条件语句
3. **状态转换复杂**：状态转换逻辑复杂，需要清晰管理
4. **状态驱动的业务**：如订单系统、工作流审批、游戏角色状态等

## 八、实际应用示例

### 8.1 订单系统
- 待支付 → 已支付 → 已发货 → 已完成
- 待支付 → 已取消

### 8.2 工作流审批
- 草稿 → 待审核 → 审核通过/审核拒绝 → 已发布

### 8.3 游戏角色状态
- 正常 → 受伤 → 无敌 → 死亡

### 8.4 线程状态
- NEW → RUNNABLE → BLOCKED → WAITING → TIMED_WAITING → TERMINATED

## 九、总结

状态模式通过将状态相关的行为封装到独立的类中，有效地消除了复杂的条件语句，使代码更加清晰、可维护。虽然会增加类的数量，但在状态转换复杂、状态行为差异大的场景下，状态模式是一个非常优秀的解决方案。
