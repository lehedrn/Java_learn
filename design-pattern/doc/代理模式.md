# 代理模式

## 一、概述

代理模式（Proxy Pattern）是一种结构型设计模式，它允许你用一个对象来代表另一个对象。代理对象控制对原始对象的访问，可以在不改变目标对象的情况下，通过一些额外的处理来控制或增强对目标对象的访问。

**核心思想**：为其他对象提供一种代理以控制对这个对象的访问。

## 二、代理模式的结构

代理模式包含以下三个核心角色：

1. **抽象主题（Subject）**：定义真实主题和代理的共同接口或抽象类
2. **真实主题（Real Subject）**：被代理的真实对象，包含具体的业务逻辑
3. **代理主题（Proxy）**：代理对象，内部持有真实主题的引用，并在调用真实主题前后进行额外处理

在本项目中：
- **抽象主题**：`UserService` 接口（[UserService.java](../src/main/java/com/coderlee/designpattern/structural/proxy/UserService.java)）
- **真实主题**：`UserServiceImpl` 实现类（[UserServiceImpl.java](../src/main/java/com/coderlee/designpattern/structural/proxy/UserServiceImpl.java)）
- **代理主题**：各种代理类（见下文）

## 三、代理模式的分类

### 3.1 静态代理

**特点**：
- 代理类在编译期就已确定
- 一个代理类只能代理一个目标类
- 代理类和目标类需要实现相同的接口或继承相同的父类

**示例代码**：
- 代理类：[UserServiceProxy.java](../src/main/java/com/coderlee/designpattern/structural/proxy/staticproxy/UserServiceProxy.java)

该代理类实现了 `UserService` 接口，持有 `UserServiceImpl` 的引用，在调用真实方法前后记录执行时间。

**使用方式**：
```
java
UserService us = new UserServiceImpl();
UserService userService = new UserServiceProxy(us);
userService.saveUser(user);
```
**优点**：
- 在编译期就确定了代理关系，类型安全
- 无需反射，性能较好
- 代码结构清晰，易于理解

**缺点**：
- 每个代理类只能代理一个特定的目标类，扩展性差
- 如果接口增加方法，代理类和实现类都要修改，违反开闭原则

### 3.2 JDK 动态代理

**特点**：
- 基于 Java 反射机制实现
- 只能代理实现了接口的类
- 代理对象和目标对象实现相同的接口
- 通过 `InvocationHandler` 拦截方法调用

**核心组件**：

1. **InvocationHandler 实现类**：[CalcTimeHandler.java](../src/main/java/com/coderlee/designpattern/structural/proxy/dynamic/jdk/CalcTimeHandler.java)
   - 实现 `InvocationHandler` 接口
   - 通过 `invoke()` 方法拦截并处理方法调用
   - 在方法执行前后记录时间

2. **代理工厂类**：[JDKProxyFactory.java](../src/main/java/com/coderlee/designpattern/structural/proxy/dynamic/jdk/JDKProxyFactory.java)
   - 使用 `Proxy.newProxyInstance()` 创建代理对象
   - 指定类加载器、接口数组和 InvocationHandler

**使用方式**：
```
java
UserService us = new UserServiceImpl();
JDKProxyFactory jdkProxyFactory = new JDKProxyFactory(us);
UserService userService = (UserService) jdkProxyFactory.getProxyInstance();
userService.saveUser(user);
```
**优点**：
- 运行时动态生成代理类，无需手动编写代理代码
- 一个处理器可以代理所有实现了相同接口的类
- 灵活性强，符合开闭原则

**缺点**：
- 只能代理实现了接口的类
- 基于反射，性能相对较差

### 3.3 Cglib 动态代理

**特点**：
- 通过继承目标类的方式创建代理
- 可以代理没有实现接口的类
- 使用 `MethodInterceptor` 拦截方法调用
- 底层使用 ASM 字节码生成框架

**核心组件**：

1. **MethodInterceptor 实现类**：[CalcTimeInterceptor.java](../src/main/java/com/coderlee/designpattern/structural/proxy/dynamic/cglib/CalcTimeInterceptor.java)
   - 实现 `MethodInterceptor` 接口
   - 通过 `intercept()` 方法拦截方法调用
   - 使用 `MethodProxy.invokeSuper()` 调用父类方法（性能优于反射）

2. **代理工厂类**：[CglibProxyFactory.java](../src/main/java/com/coderlee/designpattern/structural/proxy/dynamic/cglib/CglibProxyFactory.java)
   - 使用 Cglib 的 `Enhancer` 增强器创建代理
   - 设置目标类为父类，注册 MethodInterceptor 回调

**目标类**（无需实现接口）：[UserDao.java](../src/main/java/com/coderlee/designpattern/structural/proxy/dynamic/cglib/UserDao.java)

**使用方式**：
```
java
UserDao ud = new UserDao();
CglibProxyFactory cglibProxyFactory = new CglibProxyFactory(ud);
UserDao userDao = (UserDao) cglibProxyFactory.getProxyInstance();
userDao.save(user);
```
**优点**：
- 可以代理没有实现接口的类
- 使用 `MethodProxy` 调用父类方法，性能优于 JDK 反射
- 灵活性高，适用于更广泛的场景

**缺点**：
- 不能代理 `final` 类和 `final` 方法
- 需要引入第三方依赖（cglib 库）
- 构造方法会被调用两次（创建代理对象时）

## 四、三种代理方式的对比

| 特性 | 静态代理 | JDK 动态代理 | Cglib 动态代理 |
|------|---------|-------------|---------------|
| **代理时机** | 编译期 | 运行期 | 运行期 |
| **实现方式** | 实现相同接口 | 实现相同接口 + 反射 | 继承目标类 |
| **是否需要接口** | 是 | 是 | 否 |
| **性能** | 最好 | 较差（反射） | 较好（MethodProxy） |
| **灵活性** | 差 | 好 | 好 |
| **扩展性** | 差 | 好 | 好 |
| **依赖** | 无 | 无（JDK 自带） | 需要 cglib 库 |
| **适用场景** | 简单、固定的代理关系 | 有接口的类 | 无接口的类 |

## 五、代理模式的应用场景

1. **远程代理**：为位于不同地址空间的对象提供本地代表（如 RPC、Web Service）
2. **虚拟代理**：延迟加载，根据需要才创建开销很大的对象（如图片预览、大文件加载）
3. **保护代理**：控制对原始对象的访问权限（如权限验证）
4. **智能代理**：访问真实对象前/后执行额外操作（如日志记录、性能监控、缓存、事务控制）
5. **AOP 实现**：Spring AOP 的底层实现就是结合了 JDK 动态代理和 Cglib 动态代理

## 六、代理模式的优缺点

### 优点
- **职责分离**：代理对象可以在不修改目标对象的前提下，增加额外的功能
- **开闭原则**：动态代理可以在不修改现有代码的情况下扩展功能
- **控制访问**：可以控制对目标对象的访问时机和方式
- **降低耦合**：客户端只需要和代理对象交互，降低了与真实主题的耦合

### 缺点
- **增加系统复杂度**：引入了代理层，增加了系统的复杂性
- **性能开销**：动态代理基于反射或字节码生成，会带来一定的性能开销
- **请求延迟**：某些代理（如远程代理、虚拟代理）可能会增加响应时间

## 八、总结

代理模式是一种强大且常用的设计模式，通过引入代理对象，可以在不改变目标对象的情况下控制对它的访问或增加额外功能。

- **静态代理**适合代理关系固定、简单的场景
- **JDK 动态代理**适合目标对象实现了接口的场景，是 Spring AOP 的首选方案
- **Cglib 动态代理**适合目标对象没有实现接口的场景，作为 JDK 动态代理的补充

在实际开发中，应根据具体需求选择合适的代理方式。例如，Spring 框架在 AOP 实现中就采用了策略模式：如果目标对象实现了接口，优先使用 JDK 动态代理；否则使用 Cglib 动态代理。
