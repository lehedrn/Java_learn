# 观察者模式

## 一、概述

**观察者模式（Observer Pattern）** 是一种行为型设计模式，它定义对象间的一种**一对多**的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并被自动更新。

### 1.1 核心思想

- **一对多依赖**：一个被观察者可以被多个观察者观察
- **自动通知**：被观察者状态改变时，自动通知所有观察者
- **松耦合**：被观察者和观察者之间松耦合，可以独立变化

### 1.2 解决的问题

1. **对象间联动**
   - 一个对象的变化需要通知其他对象
   - 需要通知的对象数量不确定

2. **紧耦合问题**
   - 对象间直接调用导致紧耦合
   - 难以独立复用和测试

3. **扩展性差**
   - 新增观察者需要修改现有代码
   - 违反开闭原则

### 1.3 生活中的例子

| 场景 | 被观察者 | 观察者 |
|------|---------|--------|
| **微信公众号** | 公众号 | 粉丝 |
| **邮件订阅** | 邮件列表 | 订阅用户 |
| **抖音订阅** | UP 主 | 粉丝 |
| **气象站** | 气象传感器 | 显示屏 |
| **订单系统** | 订单状态 | 短信/邮件/物流 |

## 二、四种实现方式

本实现展示了观察者模式的**四种不同实现方式**，分别适用于不同的场景：

| 实现方式 | 场景 | 特点 | 适用场景 |
|---------|------|------|---------|
| **同步阻塞** | 微信公众号通知 | 简单、可靠 | 观察者少、执行快 |
| **异步非阻塞** | 电商订单通知 | 并行、不阻塞 | 观察者多、执行慢 |
| **事件总线** | 用户注册事件 | 解耦、灵活 | 模块解耦、同一进程 |
| **消息队列** | 支付成功事件 | 跨服务、可靠 | 微服务、分布式 |

## 三、实现方式一：同步阻塞

### 3.1 场景介绍

**微信公众号通知**：公众号发布文章时，同步通知所有粉丝，粉丝逐个接收推送。

### 3.2 类图

```
┌─────────────────────────┐
│      Observer           │
│    (观察者接口)          │
├─────────────────────────┤
│ + update(message)       │
│ + getName()             │
└───────────┬─────────────┘
            │ implements
    ┌───────┴───────┐
    │     Fan       │
    │  (具体观察者)  │
    └───────────────┘
            ▲
            │ 观察
┌───────────┴───────────┐
│   OfficialAccount     │
│    (被观察者)         │
├───────────────────────┤
│ + attach(fan)         │
│ + detach(fan)         │
│ + publishArticle()    │
└───────────────────────┘
```

### 3.3 核心代码

```java
// Observer.java - 观察者接口
public interface Observer {
    void update(String message);
    String getName();
}

// Fan.java - 具体观察者（粉丝）
public class Fan implements Observer {
    private final String name;

    @Override
    public void update(String message) {
        System.out.println("📱 粉丝 [" + name + "] 收到推送：" + message);
    }

    @Override
    public String getName() {
        return name;
    }
}

// OfficialAccount.java - 被观察者（公众号）
public class OfficialAccount {
    private final List<Observer> fans = new ArrayList<>();

    public void attach(Observer fan) {
        fans.add(fan);
    }

    public void detach(Observer fan) {
        fans.remove(fan);
    }

    public void publishArticle(String article) {
        // 同步阻塞通知所有粉丝
        for (Observer fan : fans) {
            fan.update("《" + article + "》");
        }
    }
}
```

### 3.4 特点分析

| 优点 | 缺点 |
|------|------|
| 实现简单，易于理解 | 阻塞主线程 |
| 保证通知顺序 | 观察者多时性能差 |
| 确保每个观察者都收到 | 慢的观察者影响整体 |

### 3.5 输出示例

```

📱 粉丝 [张三] 收到推送：《深入理解观察者模式》
📱 粉丝 [李四] 收到推送：《深入理解观察者模式》
📱 粉丝 [王五] 收到推送：《深入理解观察者模式》
⏱️ 同步通知完成，耗时：402ms
```

## 四、实现方式二：异步非阻塞

### 4.1 场景介绍

**电商订单状态通知**：订单状态变更时，异步通知短信、邮件、APP 推送、物流同步等多个服务。

### 4.2 类图

```
┌─────────────────────────┐
│      Observer           │
└───────────┬─────────────┘
            │
    ┌───────┼───────────────────────────────┐
    │       │       │                       │
    ▼       ▼       ▼                       ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌──────────┐
│  短信  │ │  邮件  │ │ APP   │ │  物流    │
│  服务  │ │  服务  │ │ 推送   │ │  同步    │
└────────┘ └────────┘ └────────┘ └──────────┘
            ▲
            │ 订阅
┌───────────┴───────────┐
│    OrderService       │
│  (使用线程池异步通知)   │
└───────────────────────┘
```

### 4.3 核心代码

```java
// OrderService.java - 订单服务
public class OrderService {
    private final List<Observer> observers = new ArrayList<>();
    private final ExecutorService executor = Executors.newFixedThreadPool(4);

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void updateOrderStatus(String orderId, String status, String message) {
        // 异步通知所有观察者
        List<CompletableFuture<Void>> futures = new ArrayList<>();
        for (Observer observer : observers) {
            CompletableFuture<Void> future = CompletableFuture.runAsync(() -> {
                observer.update(orderId, status, message);
            }, executor);
            futures.add(future);
        }
        // 等待所有任务完成
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
    }
}
```

### 4.4 特点分析

| 优点 | 缺点 |
|------|------|
| 不阻塞主线程 | 实现复杂 |
| 并行执行，速度快 | 线程安全问题 |
| 某个观察者失败不影响其他 | 调试困难 |

## 五、实现方式三：事件总线

### 5.1 场景介绍

**用户注册事件处理**：用户注册成功后，通过事件总线通知邮件服务、数据服务、日志服务、优惠券服务。

```
├─────────────────────────┤
│ + onEvent(event)        │
└───────────┬─────────────┘
            │ implements
    ┌───────┼───────────────────────────────┐
    │       │       │                       │
    ▼       ▼       ▼                       ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌──────────┐
│ 邮件   │ │ 数据   │ │ 日志   │ │ 优惠券   │
│ 发送   │ │ 初始化 │ │ 记录   │ │ 发放     │
└────────┘ └────────┘ └────────┘ └──────────┘
            ▲
            │ 订阅
┌───────────┴───────────┐
│      EventBus         │
│   (事件总线)          │
├───────────────────────┤
│ + subscribe()         │

│ + publish()           │
└───────────────────────┘
```

### 5.3 核心代码

```java
// Event.java - 事件基类
public abstract class Event {
    private final Object source;
    private final long timestamp;
    // ...
}

// UserRegisterEvent.java - 用户注册事件
public class UserRegisterEvent extends Event {
    private final String userId;
    private final String username;
    private final String email;
    // ...
}

// EventBus.java - 事件总线
public class EventBus {
    private final Map<Class<? extends Event>, List<EventListener>> listeners;

    public void subscribe(Class<? extends Event> eventClass, EventListener listener) {
        listeners.computeIfAbsent(eventClass, k -> new CopyOnWriteArrayList<>());
        listeners.get(eventClass).add(listener);
    }

    public void publish(Event event) {
        List<EventListener> listenerList = listeners.get(event.getClass());
        for (EventListener listener : listenerList) {
            listener.onEvent(event);
        }
    }
}
```

### 5.4 特点分析

| 优点 | 缺点 |
|------|------|
| 按事件类型订阅 | 需要维护事件映射 |
| 解耦发布者和订阅者 | 事件类型多时复杂 |
| 支持多订阅者 | 同步执行可能阻塞 |

## 六、实现方式四：消息队列（模拟）

### 6.1 场景介绍

**微服务支付事件处理**：支付成功后，消息发布到消息队列，订单服务、库存服务、积分服务、通知服务订阅处理。

### 6.3 核心代码

```java
// Message.java - 消息接口
public interface Message {
    String getType();
    String getContent();
    long getTimestamp();
}

// PaymentSuccessMessage.java - 支付成功消息
public class PaymentSuccessMessage implements Message {
    private final String orderId;
    private final String userId;
    private final double amount;
    private final String paymentMethod;
    // ...
}

// MessageQueue.java - 消息队列
public class MessageQueue {
    private final Map<String, List<MessageSubscriber>> subscribers;

    public void subscribe(String topic, MessageSubscriber subscriber) {
        subscribers.computeIfAbsent(topic, k -> new CopyOnWriteArrayList<>());
        subscribers.get(topic).add(subscriber);
    }

    public void publish(String topic, Message message) {
        List<MessageSubscriber> subscriberList = subscribers.get(topic);
        for (MessageSubscriber subscriber : subscriberList) {
            subscriber.onMessage(message);
        }
    }
}
```

### 6.4 特点分析

| 优点 | 缺点 |
|------|------|
| 跨服务解耦 | 架构复杂 |
| 消息持久化 | 运维成本高 |
| 支持重试 | 需要消息中间件 |
| 最终一致性 | 学习曲线陡 |

## 八、四种实现方式对比

### 8.1 性能对比

| 实现方式 | 通知 4 个观察者耗时 | 线程模型 |
|---------|------------------|---------|
| **同步阻塞** | ~400ms | 单线程 |
| **异步非阻塞** | ~500ms | 多线程并行 |
| **事件总线** | ~380ms | 单线程 |
| **消息队列** | ~390ms | 单线程（模拟） |

### 8.2 使用场景对比

| 实现方式 | 推荐场景 | 不推荐场景 |
|---------|---------|-----------|
| **同步阻塞** | 观察者少、执行快、需要保证顺序 | 观察者多、执行慢 |
| **异步非阻塞** | 观察者多、执行慢、实时性要求高 | 需要严格顺序 |
| **事件总线** | 同一进程内模块解耦 | 跨进程通信 |
| **消息队列** | 微服务、分布式系统 | 简单应用场景 |

### 8.3 实现复杂度对比

| 实现方式 | 代码量 | 技术难度 | 调试难度 |
|---------|-------|---------|---------|
| **同步阻塞** | ⭐ | ⭐ | ⭐ |
| **异步非阻塞** | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| **事件总线** | ⭐⭐ | ⭐⭐ | ⭐⭐ |

## 九、优缺点分析

### 9.1 优点

1. **松耦合**
   - 被观察者和观察者独立变化
   - 符合开闭原则

2. **支持广播**
   - 可以通知多个观察者
   - 观察者数量不确定

3. **易于扩展**
   - 新增观察者无需修改现有代码
   - 符合开闭原则

### 9.2 缺点

1. **性能问题**
   - 观察者多时通知耗时
   - 同步方式可能阻塞

2. **依赖不明**
   - 观察者过多时难以追踪
   - 可能导致循环依赖

3. **更新顺序**
   - 观察者执行顺序不确定
   - 有依赖关系时需谨慎

## 十、与其他模式的关系

### 10.1 观察者模式 vs 发布 - 订阅模式

| 对比项 | 观察者模式 | 发布 - 订阅模式 |
|--------|-----------|---------------|
| **耦合度** | 观察者知道被观察者 | 完全解耦 |
| **实现** | 简单 List | 消息代理/中间件 |
| **场景** | 单一应用内 | 跨应用/分布式 |

### 10.2 观察者模式 vs 责任链模式

| 对比项 | 观察者模式 | 责任链模式 |
|--------|-----------|-----------|
| **通知方式** | 广播所有 | 依次传递 |
| **执行顺序** | 同时/无序 | 有序 |

### 10.3 观察者模式 vs 中介者模式

| 对比项 | 观察者模式 | 中介者模式 |
|--------|-----------|-----------|
| **通信方式** | 一对多广播 | 多对多集中 |
| **复杂度** | 低 | 高 |

## 十一、最佳实践

### 11.1 设计建议

1. **选择合适的实现方式**
   - 观察者少：同步阻塞
   - 观察者多：异步非阻塞
   - 模块解耦：事件总线
   - 跨服务：消息队列

2. **避免内存泄漏**
   - 及时取消订阅
   - 使用弱引用

3. **处理异常**
   - 单个观察者异常不影响其他
   - 异步方式注意线程安全

### 11.2 注意事项

1. **循环依赖**
   - 观察者不应触发被观察者的变化
   - 避免无限循环

2. **性能优化**
   - 异步方式注意线程池大小
   - 批量通知可考虑分组

3. **调试技巧**
   - 记录日志便于追踪
   - 异步方式使用调试工具

## 十二、总结

观察者模式是**行为型模式**中最经典、最常用的模式之一，它通过**一对多的依赖关系**实现了对象间的自动通知。

**关键要点：**
- 被观察者：管理观察者列表，状态改变时通知
- 观察者：接收通知并作出反应
- 松耦合：双方可以独立变化

**四种实现方式：**
1. **同步阻塞**：简单可靠，适合观察者少的场景
2. **异步非阻塞**：并行高效，适合观察者多的场景
3. **事件总线**：解耦灵活，适合模块解耦
4. **消息队列**：跨服务可靠，适合微服务架构

**经典应用：**
- 微信公众号订阅
- 邮件列表服务
- Spring 事件机制
- RabbitMQ/Kafka 消息队列

观察者模式让你能够实现**事件驱动**的架构，是构建响应式和松耦合系统的重要工具！
