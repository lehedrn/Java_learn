# 职责链模式 (Chain of Responsibility Pattern)

> 使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递该请求，直到有一个对象处理它为止。
>
> —— 《设计模式：可复用面向对象软件的基础》

## 模式概述

### 问题由来

在软件系统中，经常会有这样的场景：**一个请求需要被多个对象中的某一个处理**，但发送者不知道具体应该由哪个对象来处理，也不知道有多少个潜在的处理者。

最直接的解决方案是使用 `if-else` 或 `switch-case` 来判断：

```java
// ❌ 糟糕的设计：高度耦合
public void processRequest(Request request) {
    if (request.getType() == RequestType.A) {
        handlerA.handle(request);
    } else if (request.getType() == RequestType.B) {
        handlerB.handle(request);
    } else if (request.getType() == RequestType.C) {
        handlerC.handle(request);
    }
    // ... 每新增一个处理者，都要修改这里
}
```

这种设计违反了 **开闭原则**（OCP）：每增加一个新的处理者，都需要修改现有代码。

### 职责链的解决方案

职责链模式通过将处理者组织成一条链来解决这个问题：

```
Client → Handler → Handler → Handler → ...
           ↓
      请求沿链传递，直到被处理
```

**核心思想**：请求的发送者不需要知道具体由哪个对象处理，只需要将请求发送到链上即可。

## 核心设计思想

### 1. 解耦发送者与接收者

```
┌─────────────┐         ┌─────────────────────────────┐
│   Client    │  ────→  │  Handler → Handler → Handler │
│  (发送者)   │         │        (接收者链)            │
└─────────────┘         └─────────────────────────────┘

发送者只需要知道链的存在，不需要了解：
- 链上有多少个处理者
- 每个处理者的具体职责
- 最终由哪个处理者处理请求
```

### 2. 动态组合职责

处理者可以在运行时动态组合，形成不同的处理链：

```java
// 标准流程
handler1.setNext(handler2).setNext(handler3);

// 快速流程
handler1.setNext(handler3);

// 强化流程
handler3.setNext(handler1).setNext(handler2);
```

### 3. 单一职责原则

每个处理者只负责一种类型的请求，职责清晰：

```
┌──────────────────┐
│ ValidationHandler│ → 只负责验证
├──────────────────┤
│  CouponHandler   │ → 只负责优惠券
├──────────────────┤
│ InventoryHandler │ → 只负责库存
└──────────────────┘
```

### 4. 开闭原则

新增处理者无需修改现有代码：

```java
// 新增一个处理器
public class NewHandler extends Handler {
    @Override
    protected boolean doHandle(Request request) {
        // 新的处理逻辑
    }
}

// 添加到链中（无需修改其他代码）
existingHandler.setNext(new NewHandler());
```

## 结构与实现

### UML 结构图

```
┌──────────────────────────────┐
│         Handler              │
│  ──────────────────────────  │
│  + setNext(Handler): Handler │
│  + handle(Request): boolean  │
│  - doHandle(Request): boolean│
└──────────────┬───────────────┘
               │
               │ 继承
               │
    ┌──────────┼──────────┬───────────┬───────────┐
    │          │          │           │           │
    ▼          ▼          ▼           ▼           ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│HandlerA│ │HandlerB│ │HandlerC│ │HandlerD│ │HandlerE│
└────────┘ └────────┘ └────────┘ └────────┘ └────────┘
```

### 核心角色

| 角色 | 职责 |
|------|------|
| **Handler（抽象处理者）** | 定义处理请求的接口，持有下一个处理者的引用 |
| **ConcreteHandler（具体处理者）** | 实现具体的处理逻辑，决定是否能处理该请求 |
| **Client（客户端）** | 构建责任链，发送请求 |

### 基础实现模板

```java
// 抽象处理者
public abstract class Handler {
    protected Handler nextHandler;

    public Handler setNext(Handler nextHandler) {
        this.nextHandler = nextHandler;
        return nextHandler;
    }

    public final boolean handle(Request request) {
        if (canHandle(request)) {
            doHandle(request);
            return true;  // 捕获式：处理后终止
        }
        if (nextHandler != null) {
            return nextHandler.handle(request);
        }
        return false;
    }

    protected abstract boolean canHandle(Request request);
    protected abstract void doHandle(Request request);
}
```

## 两种经典变体

职责链模式有两种经典的实现方式，选择哪种取决于业务需求：

### 变体一：流水线模式 (Pipeline)

**特点**：请求必须经过链上的每一个处理器，全部通过才算成功。

```java
public final boolean handle(Request request) {
    boolean result = doHandle(request);

    if (!result) {
        return false;  // 任一节点失败，整条链失败
    }

    if (nextHandler != null) {
        return nextHandler.handle(request);  // 继续传递
    }

    return true;  // 全部通过
}
```

**适用场景**：
- 订单处理（验证 → 优惠 → 库存 → 风控 → 发货）
- 审批流程（主管 → 经理 → 总监）
- 数据过滤（多个过滤器依次处理）
- Servlet Filter、Spring Interceptor

### 变体二：捕获式模式 (Captive)

**特点**：第一个能处理的处理器执行后，链条立即终止。

```java
public final boolean handle(Request request) {
    if (canHandle(request)) {
        return doHandle(request);  // 能处理就执行，然后终止
    }

    if (nextHandler != null) {
        return nextHandler.handle(request);  // 不能处理，传递给下一个
    }

    return false;  // 无合适处理者
}
```

**适用场景**：
- 事件处理（DOM 事件冒泡）
- 异常处理（try-catch 链）
- URL 路由（第一个匹配的路由）
- 支付渠道选择

### 两种变体的对比

| 维度 | 流水线模式 | 捕获式模式 |
|------|-----------|-----------|
| **传递规则** | 每个节点都必须执行 | 第一个能处理的节点执行后停止 |
| **成功条件** | 全部节点通过 | 任意节点处理即可 |
| **返回值含义** | true = 全部通过 | true = 已处理 |
| **典型方法签名** | `doHandle()` | `canHandle()` + `doHandle()` |
| **代表场景** | 订单处理、审批流程 | 事件处理、路由选择 |

## 实际应用场景

### 1. Servlet Filter（过滤器链）

```java
// Servlet 规范中的 FilterChain
public void doFilter(ServletRequest request, ServletResponse response,
                     FilterChain chain) {
    // 前置处理
    if (this.needAuthenticate) {
        authenticate(request);
    }

    // 传递给下一个过滤器
    chain.doFilter(request, response);

    // 后置处理
    compressResponse(response);
}
```

### 2. Spring MVC 拦截器链

```java
// Spring 中的 HandlerExecutionChain
public class HandlerExecutionChain {
    private Object handler;
    private List<HandlerInterceptor> interceptors;

    public boolean applyPreHandle(HttpServletRequest request,
                                  HttpServletResponse response) throws Exception {
        for (HandlerInterceptor interceptor : interceptors) {
            if (!interceptor.preHandle(request, response, handler)) {
                return false;  // 某个拦截器返回 false，终止
            }
        }
        return true;
    }
}
```

### 3. Netty Pipeline

```java
// Netty 中的 ChannelPipeline
ChannelPipeline pipeline = ch.pipeline();
pipeline.addLast("decoder", new HttpServerCodec())
        .addLast("aggregator", new HttpObjectAggregator(512 * 1024))
        .addLast("handler", new SimpleHttpChannelHandler());

// 数据沿管道流动：decoder → aggregator → handler
```

### 4. 异常处理机制

```java
// 异常处理的本质也是职责链
try {
    riskyOperation();
} catch (SpecificException e) {
    // 处理器 1：处理特定异常
} catch (GeneralException e) {
    // 处理器 2：处理通用异常
} catch (Exception e) {
    // 处理器 3：兜底处理
}
```

### 5. 审批流程

```
员工申请 → 主管审批 → 经理审批 → 总监审批 → HR 备案
    ↓          ↓          ↓          ↓
  金额<1k    金额<5k    金额<20k   金额>=20k
```

### 6. 日志系统

```java
// 日志级别链：DEBUG → INFO → WARN → ERROR
Logger logger = new Logger();
logger.setNext(new DebugHandler())
      .setNext(new InfoHandler())
      .setNext(new WarnHandler())
      .setNext(new ErrorHandler());

// 发送 INFO 级别日志，WARN 和 ERROR 处理器会忽略
```

## 与其他模式的对比

### 1. 职责链 vs 策略模式

| 维度 | 职责链模式 | 策略模式 |
|------|-----------|---------|
| **目的** | 多个对象处理同一请求 | 封装可互换的算法 |
| **结构** | 链式结构，顺序传递 | 平行结构，选择一个 |
| **客户端** | 发送请求到链上 | 主动选择策略 |
| **耦合度** | 发送者与接收者解耦 | 客户端与策略耦合 |

**代码对比**：

```java
// 职责链：客户端不知道谁处理
chain.handle(request);

// 策略：客户端主动选择
Strategy strategy = new ConcreteStrategyA();
strategy.execute(request);
```

**组合使用**：职责链中可以使用策略模式来选择不同的处理方式。

### 2. 职责链 vs 装饰器模式

| 维度 | 职责链模式 | 装饰器模式 |
|------|-----------|-----------|
| **目的** | 多个对象有机会处理请求 | 动态给对象添加职责 |
| **传递** | 可以选择不处理，传递给下一个 | 必须调用被装饰者 |
| **结构** | 链式 | 嵌套包裹 |

```java
// 职责链：可以选择传递
handler.handle(request);

// 装饰器：层层调用
decoratedComponent.operation();  // 外层 → 内层 → 核心
```

### 3. 职责链 vs 命令模式

| 维度 | 职责链模式 | 命令模式 |
|------|-----------|---------|
| **关注点** | 如何传递请求 | 如何封装请求 |
| **结构** | 链式传递 | 队列/日志/撤销 |

### 4. 职责链 + 命令模式（组合使用）

```java
// 命令可以作为请求在职责链中传递
public class CommandHandler extends Handler {
    public boolean handle(Command command) {
        if (canExecute(command)) {
            command.execute();
            return true;
        }
        if (nextHandler != null) {
            return nextHandler.handle(command);
        }
        return false;
    }
}
```

### 5. 职责链 + 工厂模式（组合使用）

```java
// 使用工厂创建处理者
public class HandlerFactory {
    public static Handler createChain() {
        Handler h1 = new ValidationHandler();
        Handler h2 = new AuthHandler();
        Handler h3 = new BusinessHandler();

        h1.setNext(h2).setNext(h3);
        return h1;
    }
}
```

## 优缺点分析

### 优点

1. **降低耦合度**
   - 发送者不需要知道接收者的详细信息
   - 链上的处理者也不需要知道链的结构

2. **增强给对象指派职责的灵活性**
   - 可以动态改变链内的成员
   - 可以动态调整次序

3. **符合单一职责原则**
   - 每个类只负责一个职责
   - 职责清晰，便于维护

4. **符合开闭原则**
   - 增加新的处理者无需修改现有代码
   - 只需添加到链中即可

5. **简化对象的相互连接**
   - 只需要持有下一个处理者的引用
   - 不需要维护所有可能处理者的引用

### 缺点

1. **调试困难**
   - 链条过长时，难以追踪请求的传递路径
   - 需要完善的日志系统

2. **性能影响**
   - 每次请求可能要遍历多个节点
   - 链条过长会影响性能

3. **无保证处理**
   - 捕获式模式下，请求可能没有被任何节点处理
   - 需要兜底处理逻辑

4. **循环引用风险**
   - 如果不小心形成循环引用，会导致死循环
   - 需要在使用时注意链的构建

5. **内存占用**
   - 每个处理者都需要持有下一个处理者的引用
   - 对于短生命周期的请求，可能造成内存浪费

## 最佳实践

### 1. 链条长度控制

```java
// ✅ 建议：链条不超过 5-7 个节点
handler1.setNext(handler2).setNext(handler3)
        .setNext(handler4).setNext(handler5);

// ❌ 避免：过长的链条难以维护
handler1.setNext(handler2).setNext(handler3)
        .setNext(handler4).setNext(handler5)
        .setNext(handler6).setNext(handler7)
        .setNext(handler8).setNext(handler9)
        .setNext(handler10);
```

### 2. 日志追踪

```java
public abstract class Handler {
    protected void log(String message, Request request) {
        System.out.println("[" + getClass().getSimpleName() + "] "
                          + "Request[" + request.getId() + "]: "
                          + message);
    }
}
```

### 3. 明确失败处理

```java
// 明确定义节点失败时的行为
public final boolean handle(Request request) {
    if (!canHandle(request)) {
        if (nextHandler != null) {
            return nextHandler.handle(request);
        }
        // 兜底处理
        return handleNoSuitableHandler(request);
    }
    return doHandle(request);
}

protected boolean handleNoSuitableHandler(Request request) {
    // 记录日志、发送告警、返回默认值等
    return false;
}
```

### 4. 防止循环引用

```java
// 构建链时检查
public Handler setNext(Handler nextHandler) {
    // 检查是否形成循环
    Handler current = nextHandler;
    while (current != null) {
        if (current == this) {
            throw new IllegalStateException("循环引用检测");
        }
        current = current.nextHandler;
    }
    this.nextHandler = nextHandler;
    return nextHandler;
}
```

### 5. 使用构建器模式组装链

```java
public class HandlerChainBuilder {
    private Handler head;
    private Handler tail;

    public HandlerChainBuilder add(Handler handler) {
        if (head == null) {
            head = handler;
            tail = handler;
        } else {
            tail.setNext(handler);
            tail = handler;
        }
        return this;
    }

    public Handler build() {
        return head;
    }
}

// 使用
Handler chain = new HandlerChainBuilder()
    .add(new ValidationHandler())
    .add(new AuthHandler())
    .add(new BusinessHandler())
    .build();
```

### 6. 模式选择指南

```
需要所有步骤都执行吗？
    │
    ├── 是 → 流水线模式
    │       （订单处理、审批流程、过滤器）
    │
    └── 否 → 捕获式模式
            （事件处理、路由选择、异常处理）
```

## 总结

职责链模式是一种强大且灵活的行为型设计模式，它通过**解耦发送者与接收者**、**动态组合职责**、**遵循单一职责和开闭原则**，使得系统更加模块化、可扩展。

**关键要点**：
1. 选择合适的变体：流水线 vs 捕获式
2. 控制链条长度，避免过长
3. 添加完善的日志追踪
4. 明确失败和兜底处理
5. 可以与其他模式组合使用

**何时使用**：
- 有多个对象可以处理同一请求
- 发送者不知道具体由哪个对象处理
- 处理对象可以动态组合
- 希望解耦发送者与接收者

**何时不使用**：
- 请求的处理者是确定的
- 链条过长影响性能
- 需要调试每个处理步骤
