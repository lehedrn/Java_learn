# 桥接模式

## 一、概述

**桥接模式（Bridge Pattern）** 是一种结构型设计模式，它将抽象部分与实现部分分离，使它们可以独立地变化。

### 1.1 核心思想

- 使用**组合/聚合关系**代替继承关系
- 将两个或多个维度的变化分离，通过桥接连接起来
- 让不同维度可以独立扩展，互不影响

### 1.2 解决的问题

传统的继承机制会导致"类爆炸"问题。例如，如果有两种变化维度（消息类型和发送方式），使用继承会产生 M×N 个类。桥接模式通过将这两个维度分离，只需要 M+N 个类即可。

## 二、模式结构

### 2.1 角色组成

1. **抽象化角色（Abstraction）** - [`Message`](../src/main/java/com/coderlee/designpattern/behavioral/brige/Message.java)
   - 定义抽象类的接口
   - 维护一个指向实现化角色的引用
   - 通过组合关系委托给实现化角色

2. **修正抽象化角色（Refined Abstraction）** 
   - [`NormalMessage`](../src/main/java/com/coderlee/designpattern/behavioral/brige/NormalMessage.java) - 普通消息
   - [`UrgentMessage`](../src/main/java/com/coderlee/designpattern/behavioral/brige/UrgentMessage.java) - 紧急消息
   - 继承自抽象化角色，实现具体的业务逻辑

3. **实现化角色（Implementor）** - [`MessageSender`](../src/main/java/com/coderlee/designpattern/behavioral/brige/MessageSender.java)
   - 定义实现类的接口
   - 该接口不一定与抽象化角色的接口完全对应

4. **具体实现化角色（Concrete Implementor）**
   - [`SmsSender`](../src/main/java/com/coderlee/designpattern/behavioral/brige/SmsSender.java) - 短信发送器
   - [`EmailSender`](../src/main/java/com/coderlee/designpattern/behavioral/brige/EmailSender.java) - 邮件发送器
   - [`WechatSender`](../src/main/java/com/coderlee/designpattern/behavioral/brige/WechatSender.java) - 微信发送器
   - 实现实现化角色定义的接口，提供具体的实现逻辑

## 四、优缺点分析

### 4.1 优点

1. **解耦抽象和实现**
   - 抽象部分和实现部分可以独立变化和扩展
   - 符合**开闭原则**（对扩展开放，对修改关闭）

2. **避免类爆炸**
   - 使用组合代替继承，大大减少类的数量
   - 例如：M 种消息类型 × N 种发送方式
     - 继承方式：M×N 个类
     - 桥接模式：M+N 个类

3. **更高的灵活性**
   - 可以在运行时动态组合不同的抽象和实现
   - 支持更细粒度的共享和复用

4. **符合合成复用原则**
   - 优先使用组合/聚合，而非继承

### 4.2 缺点

1. **增加理解难度**
   - 需要识别出系统中的两个独立维度
   - 设计复杂度较高

2. **正确性依赖设计**
   - 如果维度划分不当，可能导致模式失效
   - 需要对系统进行深入分析

3. **增加代码量**
   - 需要定义更多的接口和抽象类
   - 初始开发成本较高

## 五、适用场景

### 5.1 适合使用桥接模式的场景

1. **系统存在多个变化维度**
   - 每个维度都可以独立扩展
   - 需要在多个维度之间进行组合

2. **需要避免继承爆炸**
   - 使用继承会导致类的数量急剧增加
   - 希望用更少的类实现更多的功能组合

3. **抽象和实现需要独立扩展**
   - 抽象部分和实现部分都不应该影响对方
   - 需要更高的灵活性和可扩展性

4. **运行时动态绑定**
   - 需要在运行时动态切换实现
   - 而不是在编译时静态绑定

### 5.2 实际应用示例

1. **图形绘制系统**
   - 维度 1：形状（圆形、矩形、三角形）
   - 维度 2：颜色（红色、蓝色、绿色）
   - 使用桥接模式：形状 × 颜色 可以任意组合

2. **消息通知系统**（本代码示例）
   - 维度 1：消息类型（普通、紧急、加急）
   - 维度 2：通知渠道（短信、邮件、微信、APP 推送）

3. **数据库驱动**
   - JDBC API 就是桥接模式的典型应用
   - 抽象：JDBC 标准接口
   - 实现：各数据库厂商的驱动程序

4. **跨平台 UI 框架**
   - 维度 1：控件类型（按钮、文本框、列表）
   - 维度 2：平台实现（Windows、Mac、Linux）

## 六、与其他模式的关系

### 6.1 桥接模式 vs 适配器模式

- **桥接模式**：预先设计好的结构，将两个维度连接起来
- **适配器模式**：事后补救，让不兼容的接口能够一起工作

### 6.2 桥接模式 vs 策略模式

- **桥接模式**：关注抽象和实现的分离，结构更稳定
- **策略模式**：关注算法的可替换性，更灵活

### 6.3 桥接模式 vs 状态模式

- **桥接模式**：实现部分的委托关系相对固定
- **状态模式**：对象的行为随状态变化而动态改变

### 6.4 与单例模式的结合

- 具体实现化角色可以设计为单例
- 例如：`SmsSender.getInstance()`

## 七、最佳实践

### 7.1 设计建议

1. **正确识别变化维度**
   - 找出系统中真正独立的变化轴
   - 不要为了用模式而强行拆分

2. **保持接口一致性**
   - 实现化角色的接口应该足够通用
   - 能够支持所有抽象化角色的需求

3. **合理使用组合**
   - 抽象化角色持有实现化角色的引用
   - 可以通过构造器注入或 Setter 方法

### 7.2 扩展示例

参考代码目录，如需新增：

- **新增消息类型**：继承 `Message` 类，如 [`NormalMessage`](../src/main/java/com/coderlee/designpattern/behavioral/brige/NormalMessage.java)

## 八、总结

桥接模式是一种优秀的结构型模式，它通过**组合优于继承**的设计原则，实现了抽象和实现的解耦。虽然增加了系统的复杂度，但在处理多维度变化时表现出色，是应对类爆炸问题的有效手段。

**关键要点：**
- 识别独立变化的维度
- 使用组合代替继承
- 遵循开闭原则
- 提高系统的可扩展性
