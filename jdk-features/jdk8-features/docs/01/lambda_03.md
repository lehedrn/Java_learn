# 深入理解 Java 8 Lambda（三）：作用域、变量捕获与内存语义（核心原理篇）

> **阅读定位**
> * 为什么 Lambda **必须**要求 effectively final
> * 为什么并行 Stream 一不小心就出事故
> * 为什么 Lambda 在并发语义上比匿名内部类“更克制”
>
> 那这篇文章，值得你慢慢读。

---

## 一、一个看似简单，却牵扯整个内存模型的问题

先看一段所有人都见过的代码：

```java
int x = 10;
Runnable r = () -> System.out.println(x);
x = 20; // ❌ 编译错误
```

很多解释会停留在一句话：

> “Lambda 捕获的局部变量必须是 effectively final。”

**但这句话本身并没有解释任何东西。**

真正的问题是：

> **如果 Java 允许这样写，会发生什么？
> 在单线程、跨线程、延迟执行的情况下，它是否还能保持一致的内存语义？**

答案是：**不能**。
而 Java 选择的是：**在语言层面直接禁止这种不确定性**。

---

## 二、Lambda 的作用域模型：它并没有“自己的世界”

### 1. Lambda 没有独立作用域（这是很多误解的根源）

先给出一个非常重要的结论：

> **Lambda 不会创建新的作用域。**

这意味着：

* Lambda 不是一个“代码块”
* Lambda 更像是**嵌入在当前作用域中的一段行为描述**

```java
int x = 10;
Runnable r = () -> {
    // 这里并不是一个新的局部作用域
};
```

这点和匿名内部类**本质不同**。

---

### 2. this / super 的语义差异（与匿名内部类对比）

这是一个极其关键、但常被忽略的区别。

| 场景        | Lambda | 匿名内部类 |
| --------- | ------ | ----- |
| `this` 指向 | 外部类实例  | 内部类实例 |
| 是否产生新对象   | 不一定    | 一定    |
| 语义更接近     | 方法调用   | 对象定义  |

这直接影响两点：

1. **对象逃逸分析**
2. **并发可见性与发布语义**

Lambda 更像是“方法级行为”，而不是“对象级结构”。

---

### 3. 为什么 Lambda 不能 shadow（遮蔽）外部局部变量？

```java
int x = 10;
Runnable r = () -> {
    int x = 20; // ❌
};
```

原因不是“语法限制”，而是：

> **Lambda 运行在外层作用域中，
> 如果允许同名变量，将破坏作用域一致性。**

匿名内部类之所以可以，是因为它**本身就是一个新的类型和作用域**。

---

## 三、什么是变量捕获（Variable Capture）

### 1. 捕获 ≠ 访问（必须先分清）

这是理解后续一切的前提。

* **实例变量 / 静态变量**
  → Lambda 是“访问”（access）

* **局部变量**
  → Lambda 是“捕获”（capture）

这两者在 **内存模型上完全不是一回事**。

---

### 2. 捕获的到底是什么？

一个关键结论：

> **Lambda 捕获的不是“变量”，
> 而是“变量当前值的快照”。**

```java
int x = 10;
Runnable r = () -> System.out.println(x);
```

等价的底层语义是：

> 在 Lambda 创建时，`x` 的值 **被复制** 到 Lambda 的执行上下文中。

这也是为什么：

* 修改 `x` 会被禁止
* Lambda 中看到的值始终一致

---

## 四、effectively final：不是语法规则，而是内存模型选择

---

### 1. 表面规则（快速带过）

局部变量：

* 要么显式 `final`
* 要么 **effectively final**（只赋值一次）

---

### 2. 第一层深因：栈变量生命周期 vs Lambda 生命周期

* 局部变量：

    * 存在于 **栈帧**
    * 方法结束 → 栈帧销毁

* Lambda：

    * 可能被返回
    * 可能延迟执行
    * 可能在**另一个线程**执行

👉 **捕获一个“可变的栈变量”在物理上就是不安全的。**

---

### 3. 第二层深因：Java 明确选择了“值捕获模型”

如果允许捕获可变变量，语言必须处理：

* 多线程下值不一致
* 写-读可见性
* happens-before 建立

这意味着：

* 引入隐式同步
* 引入隐式 volatile
* 或者复杂的内存屏障

Java 的选择是：

> **不做。
> 直接禁止。**

---

## 五、Lambda 与 Java 内存模型（JMM）的关系（重点）

### 1. Lambda 捕获与 happens-before

一个非常重要但少有人讲清的事实：

> **被 Lambda 捕获的 final / effectively final 局部变量，
> 在 Lambda 执行时具备安全发布语义。**

原因来自 JMM 对 final 的规定：

* final 字段在构造完成后
* 对其他线程 **可见且不可变**

Lambda 捕获机制**复用了这一语义模型**。

---

### 2. 如果允许捕获可变变量，会破坏什么？

假设允许：

```java
int x = 10;
Runnable r = () -> System.out.println(x);
x = 20;
new Thread(r).start();
```

问题来了：

* r 执行时看到 10 还是 20？
* 是否需要 volatile？
* 是否建立 happens-before？

👉 **所有答案都不确定**。

Java 的设计目标是：

> **让 Lambda 在并发语义上“天然安全”**

---

## 六、对象引用捕获：为什么它“看起来能改”

```java
List<Integer> list = new ArrayList<>();
Runnable r = () -> list.add(1);
```

这是很多人产生误解的地方。

---

### 1. final 限制的是“引用”，不是对象状态

* `list` 引用不可变
* `list` 指向的对象 **完全可以变**

所以：

* 语法合法
* 语义允许

---

### 2. 并发风险从哪里来？

如果多个线程执行这个 Lambda：

* 修改的是同一个对象
* Lambda **不提供任何同步语义**

👉 并发安全与否，**完全取决于对象本身**。

---

### 3. Atomic / 数组“绕过规则”的本质

```java
AtomicInteger i = new AtomicInteger(0);
r = () -> i.incrementAndGet();
```

* 捕获的是引用
* 原子性来自 `AtomicInteger`
* 与 Lambda 无关

---

## 七、Lambda vs 匿名内部类：并发与捕获语义对比

### 1. 捕获规则的演进，而非革命

* Java 8 之前：匿名内部类必须 `final`
* Java 8：effectively final

👉 **语义没变，只是写法放宽**

---

### 2. this 语义差异带来的并发影响

* 匿名内部类：

    * 一定创建新对象
    * this 指向新实例
    * 更容易发生对象逃逸

* Lambda：

    * 可能不创建新对象
    * this 指向外部实例
    * 更接近“方法调用”

这也是 Lambda **性能与并发友好度更高**的原因之一。

---

## 八、Lambda + 并发 Stream 的安全边界（工程重点）

### 1. 一个必须反复强调的事实

> **并行 Stream ≠ 自动线程安全**

Lambda 不会：

* 自动加锁
* 自动 volatile
* 自动同步

---

### 2. 并行 Stream 中“安全”的 Lambda

* 无状态（stateless）
* 无副作用
* 纯函数

```java
stream.parallel()
      .map(x -> x * 2)
      .collect(toList());
```

---

### 3. 典型反例（真实踩坑）

```java
int sum = 0;
list.parallelStream().forEach(x -> sum += x); // ❌
```

问题不是 Lambda，问题是：

* 修改共享可变状态
* 没有 happens-before
* 没有同步

---

### 4. 为什么 reduce / collect 更安全？

因为它们：

* 定义了明确的组合规则
* 框架层面控制并发
* happens-before 关系清晰

---

## 九、工程级设计建议（从并发视角）

### 1. 把 Lambda 当成“数学函数”

* 输入 → 输出
* 无副作用

---

### 2. 一旦你想在 Lambda 中“改外部变量”，就该警惕

这通常意味着：

* 设计有问题
* 并行不可控
* 可维护性极差

---

### 3. 并发场景下的推荐模式

* 不可变对象
* 显式同步
* 函数式组合

---

## 十、总结

1. **Lambda 捕获的是值快照，而不是变量**
2. **effectively final 是 JMM 的必然结果**
3. **Lambda 的并发安全性完全由你自己保证**
