# Java 8 新特性 · 重复注解（Repeatable Annotations）深度解析

> 在 Java 8 之前，注解更像是一种“静态标记”；
> 从 Java 8 开始，注解正在演变成一种**声明式配置语言**。
> 重复注解，正是这个转变中一个容易被忽视、却非常关键的特性。

---

## 一、为什么 Java 需要「重复注解」？

### 1️⃣ Java 8 之前的现实困境

在 Java 7 及更早版本中：

> **同一个注解，在同一个位置只能出现一次**

这在很多真实业务场景中非常别扭。

例如：权限控制、拦截器、扩展点声明。

```java
@Permission("ADMIN")
@Permission("USER") // ❌ 编译失败（Java 7）
public void deleteOrder() {}
```

### 2️⃣ 传统解决方案：容器注解（但并不优雅）

```java
@Permissions({
    @Permission("ADMIN"),
    @Permission("USER")
})
public void deleteOrder() {}
```

这套写法的问题非常明显：

| 问题    | 说明              |
| ----- | --------------- |
| 可读性差  | 核心语义被“数组结构”包裹   |
| 样板代码多 | 每个可重复语义都要定义一个容器 |
| 不符合直觉 | “多个配置”却要嵌套一层    |

📌 **问题的本质**：

> Java 的注解在语法层面，无法自然表达“同类配置可叠加”。

---

## 二、重复注解的核心思想

Java 8 给出的答案是：**Repeatable Annotation**。

> **允许同一个注解，在同一声明位置出现多次。**

```java
@Permission("ADMIN")
@Permission("USER")
public void deleteOrder() {}
```

✔️ 语义直观
✔️ 可读性强
✔️ 更接近“配置”的表达方式

但这并不是 JVM 的新能力，而是一次**精心设计的语法与反射 API 协同演进**。

---

## 三、如何定义一个可重复注解？

### 1️⃣ 定义业务注解

```java
@Repeatable(Permissions.class)
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Permission {
    String value();
}
```

### 2️⃣ 定义容器注解

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Permissions {
    Permission[] value();
}
```

### 3️⃣ 使用方式（Java 8 之后）

```java
public class OrderService {

    @Permission("ADMIN")
    @Permission("USER")
    public void deleteOrder() {}
}
```

---

### 关键约束（非常重要）

| 规则                      | 说明      |
| ----------------------- | ------- |
| 必须声明 `@Repeatable`      | 指定容器注解  |
| 容器必须有 `value()`         | 类型为注解数组 |
| Target / Retention 必须一致 | 否则编译失败  |

📌 **可重复注解 ≠ 没有容器注解**
容器注解仍然存在，只是被编译器“藏”起来了。

---

## 四、编译后发生了什么？（核心原理）

这是理解重复注解的关键一节。

### 1️⃣ 源码视角

```java
@Permission("ADMIN")
@Permission("USER")
```

### 2️⃣ 编译器视角

Java 编译器会在**编译期自动合成容器注解**：

```java
@Permissions({
    @Permission("ADMIN"),
    @Permission("USER")
})
```

### 3️⃣ JVM 视角

> JVM **并不认识“重复注解”这个概念**
> JVM 只认识：**容器注解**

📌 **结论**：

> 重复注解是一个**100% 的编译期语法糖**

---

## 五、反射读取：最容易踩坑的地方

### ❌ 错误示例

```java
Permission permission =
        method.getAnnotation(Permission.class);
```

➡️ 返回 `null`

因为 JVM 层面根本不存在“多个 Permission 注解”。

---

### ✅ 正确方式：getAnnotationsByType（推荐）

```java
Permission[] permissions =
        method.getAnnotationsByType(Permission.class);

for (Permission p : permissions) {
    System.out.println(p.value());
}
```

📌 这个 API 是 **Java 8 为重复注解量身定做的**

它会自动：

* 处理容器注解
* 还原成“逻辑上的多个注解”

---

### ⚠️ 不推荐方式：直接读取容器

```java
Permissions permissions =
        method.getAnnotation(Permissions.class);
```

问题在于：

* 强依赖容器结构
* 降低注解设计的可演进性
* 与 Java 8 的设计初衷相悖

---

## 六、@Inherited 与重复注解的关系

这是一个常见误区。

结论先行：

> **@Inherited 对重复注解没有任何特殊加成**

### 原因

* `@Inherited` **只对类级别注解有效**
* 不作用于方法、字段、参数
* 子类继承的是“最终合成后的容器注解”

## 七、真实框架中的应用案例

### 1️⃣ Spring Framework

```java
@Import(A.class)
@Import(B.class)
@Configuration
public class AppConfig {}
```

📌 `@Import` 是可重复注解（Spring 4.2+）

---

### 2️⃣ JUnit 5

```java
@ExtendWith(SpringExtension.class)
@ExtendWith(MockitoExtension.class)
class MyTest {}
```

---

### 3️⃣ Java EE / Jakarta EE

```java
@HttpMethod("GET")
@HttpMethod("POST")
```

---

## 八、什么时候应该使用重复注解？

### ✅ 适合的场景

| 场景      | 示例              |
| ------- | --------------- |
| 同类配置可叠加 | 权限、拦截器          |
| 顺序有业务含义 | Filter、Pipeline |
| 数量不固定   | 扩展点声明           |

---

### ❌ 不适合的场景

| 场景      | 原因      |
| ------- | ------- |
| 强结构化配置  | 一个注解更清晰 |
| 参数之间强关联 | 明确字段更安全 |
| 单一语义    | 不要滥用    |

---

## 九、与 Java 8 整体设计的一致性

重复注解并不是一个孤立特性。

| Java 8 特性 | 核心目标      |
| --------- | --------- |
| Lambda    | 消除样板代码    |
| Stream    | 强化意图表达    |
| Optional  | 显式建模“不存在” |
| 重复注解      | 让配置可组合    |

➡️ **Java 8 的设计哲学只有一句话：**

> 让代码表达“意图”，而不是“形式”。

---

## 十、总结

> **重复注解本质上是一次非常克制的设计：**
>
> * JVM 不变
> * 字节码结构不变
> * 编译器 + 反射 API 协同进化
>
> 它让注解从“单点标记”，进化为“可叠加的声明式配置”。
