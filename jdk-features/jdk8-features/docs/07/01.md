# Java 8 CompletableFuture：从 Future 到异步计算管道

## 引言

在 Java 8 之前，Java 并不缺乏并发工具：线程池、Future、回调机制早已存在。但在真实项目中，一旦异步逻辑开始变复杂——多个任务并行、结果相互依赖、统一异常处理——代码往往迅速失控。

Java 8 引入的 `CompletableFuture`，并不是对 `Future` 的简单增强，而是一次**异步编程模型层面的升级**。
它试图解决的并不是“能不能异步执行”，而是一个更关键的问题：

> **如何优雅地描述、组合和维护复杂的异步流程？**

---

## 一、传统 Future 的能力边界

`java.util.concurrent.Future` 诞生于 Java 5，其核心职责非常明确：

> **表示一个“未来才会产生的结果”**

```java
Future<Integer> future = executor.submit(() -> compute());
Integer result = future.get(); // 阻塞
```

### 1. 被动的结果模型

Future 的能力集中在：

* `get()`：阻塞等待
* `isDone()`：轮询状态
* `cancel()`：取消任务

它并不关心：

* 结果完成之后要做什么
* 多个 Future 之间的依赖关系
* 如何组合多个异步结果

因此，很多代码最终仍然回到同步思维：

```java
Integer r1 = f1.get();
Integer r2 = f2.get();
Integer r3 = f3.get();
```

---

### 2. 无法描述异步流程

一旦业务需求出现以下场景：

* 并行调用多个远程服务
* 下一个任务依赖上一个异步结果
* 任一步失败需要统一兜底
* 不同阶段运行在不同线程池

`Future` 本身就显得力不从心。

> **Future 是结果的占位符，而不是流程的描述器。**

---

## 二、回调模型：解决了阻塞，却引入了混乱

为了解决阻塞问题，很多系统转而使用回调：

```java
asyncCall(a, r1 -> {
    asyncCall2(r1, r2 -> {
        asyncCall3(r2, r3 -> {
            // ...
        });
    });
});
```

这种模型的弊端非常明显：

* 回调地狱，代码不断右移
* 异常处理高度分散
* 业务逻辑与并发控制强耦合
* 可读性和可维护性极差

> **回调解决了“非阻塞”，却牺牲了“结构”。**

---

## 三、Java 8 的选择：CompletionStage 抽象

Java 8 没有继续在 `Future` 上修修补补，而是引入了一个新的抽象：

```java
public interface CompletionStage<T>
```

它关注的不是“结果什么时候可用”，而是：

> **当一个阶段完成时，接下来会发生什么**

`CompletableFuture` 正是 `CompletionStage` 的官方实现：

```java
public class CompletableFuture<T>
        implements Future<T>, CompletionStage<T>
```

这标志着 Java 并发模型从“结果导向”迈向了“流程导向”。

---

## 四、CompletableFuture 的核心定位

### 1. 从“获取结果”到“描述过程”

对比两种思维方式：

**Future：**

```java
Future<T> f = submit(task);
T result = f.get();
```

**CompletableFuture：**

```java
CompletableFuture<T> cf =
    CompletableFuture
        .supplyAsync(task)
        .thenApply(this::transform)
        .thenCompose(this::nextAsync);
```

在 CompletableFuture 中，重点不再是 `get()`，而是**阶段之间的依赖关系**。

---

### 2. 异步流程的声明式表达

CompletableFuture 的 API 设计明显借鉴了 Stream：

| CompletableFuture | Stream  |
| ----------------- | ------- |
| thenApply         | map     |
| thenCompose       | flatMap |
| thenCombine       | merge   |
| allOf / anyOf     | 聚合操作    |

这使得异步代码第一次具备了**清晰的结构和可读性**。

---

## 五、为什么叫 CompletableFuture？

这个命名本身就体现了设计思想。

### 1. Future：被动完成

* 任务结束 → Future 状态改变
* 使用者只能等待

---

### 2. CompletableFuture：主动完成

```java
CompletableFuture<T> cf = new CompletableFuture<>();

cf.complete(value);
cf.completeExceptionally(ex);
```

这意味着：

* 结果的生产者与消费者解耦
* 异步结果可以来自线程池、回调、IO 事件甚至手动触发

> **CompletableFuture 更像是一个“异步协议载体”，而不仅是返回值。**

---

## 六、核心 API 与使用模式概览

### 1. 创建异步任务

```java
CompletableFuture.runAsync(() -> task());
CompletableFuture.supplyAsync(() -> result());
```

* `runAsync`：无返回值
* `supplyAsync`：有返回值

⚠️ 默认使用 `ForkJoinPool.commonPool`

---

### 2. 链式处理

```java
cf.thenApply(x -> x + 1)
  .thenAccept(System.out::println);
```

* `thenApply`：转换结果
* `thenAccept`：消费结果
* `thenRun`：只关心完成事件

---

### 3. 组合异步任务

* **thenCompose**：异步依赖（扁平化）
* **thenCombine**：两个结果到齐再处理
* **allOf / anyOf**：批量编排

```java
cf1.thenCombine(cf2, (a, b) -> a + b);
```

---

## 七、异常处理模型：工程价值所在

CompletableFuture 提供了统一的异常传播机制：

* `exceptionally`：兜底
* `handle`：结果与异常统一处理
* `whenComplete`：只做收尾，不改结果

```java
cf.handle((res, ex) -> {
    if (ex != null) return fallback;
    return res;
});
```

这让异步代码第一次具备了**结构化的错误处理能力**。

---

## 八、线程模型与 commonPool 的工程陷阱

### 1. 默认线程池的风险

* `ForkJoinPool.commonPool`
* 全 JVM 共享
* 不适合阻塞 IO

```java
CompletableFuture.supplyAsync(() -> restCall()); // 潜在风险
```

一旦阻塞：

* commonPool 被耗尽
* 其他并行任务整体受影响

### 2. 工程实践建议

> **IO 场景务必使用自定义线程池**

```java
ExecutorService executor = Executors.newFixedThreadPool(10);
CompletableFuture.supplyAsync(task, executor);
```

---

## 九、CompletableFuture 的历史意义

从 Java 演进角度看：

* Java 5：线程池 + Future（并发执行）
* Java 8：CompletableFuture（并发编排）

> **CompletableFuture 标志着 Java 正式进入“声明式异步编程”时代。**

它并不是为了取代线程池或并发工具，而是为它们提供了一种**更高层次的组织方式**。

---

## 结语

CompletableFuture 的价值，并不在于 API 的数量，而在于它提供了一种新的思维模型：

* 用阶段描述异步
* 用组合表达依赖
* 用管道组织流程

理解这一点，CompletableFuture 才不会沦为“换个写法的 Future”，而会成为构建复杂异步系统的核心工具。
