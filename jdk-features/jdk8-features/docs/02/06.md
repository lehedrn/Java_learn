# 第 6 篇（进阶 / 工程向）：函数式接口的设计实践与反模式

## —— 站在架构高度的工程思考

📌 **定位**：高阶 API 设计 / 框架开发 / 架构视角

---

## 一、引言：函数式接口在架构中的价值

* 函数式接口是 Java 8 函数式编程的**核心类型单元**
* 不仅是 Lambda 的类型锚点，更是**框架回调、事件处理、策略模式的基础**
* 高阶设计思考：

    1. 类型安全 + 可组合 + 可复用
    2. 支撑高频、低延迟调用场景
    3. 保持接口纯粹，减少污染

> 本篇目标：从**API 设计哲学、函数式接口反模式、工程实践、框架级设计经验**多维度解析函数式接口。

---

## 二、优先标准接口 vs 自定义接口

### 2.1 标准接口优先原则

* **Function / Consumer / Predicate / Supplier** 是核心工具
* 优点：

    * 与 Stream / Optional / CompletableFuture 等标准库无缝衔接
    * 已定义组合方法，减少重复开发
    * 语义统一，团队协作友好

**示例**：

```java
Function<String, Integer> parseLen = String::length;
Predicate<Integer> isPositive = i -> i > 0;
Consumer<String> printer = System.out::println;
```

### 2.2 何时自定义接口

* **语义化接口**：接口名称明确业务意图
* **参数类型特殊化**：标准接口无法表达复杂约束
* **自定义组合逻辑**：需要 default 方法提供组合或流水线功能

**高级示例**：

```java
@FunctionalInterface
public interface Validator<T> {
    boolean validate(T t);

    default Validator<T> and(Validator<T> other) {
        return t -> this.validate(t) && other.validate(t);
    }

    default Validator<T> or(Validator<T> other) {
        return t -> this.validate(t) || other.validate(t);
    }
}
```

* 提供高阶组合能力
* 避免污染接口的核心方法

> 核心原则：自定义接口必须 **语义清晰 + 可组合 + 复用性高**。

## 三、函数式接口的污染问题与反模式

### 3.1 接口污染的定义

* **过多 default / static 方法**，破坏接口纯粹性
* **混入状态管理或业务逻辑**
* 结果：

    * Lambda 难以实现
    * 类型组合能力下降
    * 框架可维护性降低

### 3.2 典型反模式示例

```java
@FunctionalInterface
interface BadFunc {
    void apply(String s);
    default void log(String msg) { System.out.println(msg); }
    default void validate(String s) { if(s==null) throw new IllegalArgumentException(); }
    default void extra() { /* 不相关方法 */ }
}
```

* **问题**：Lambda 只能实现 `apply`，但默认方法太多，破坏接口设计清晰度
* **架构风险**：长期维护中接口语义模糊，增加调试成本

### 3.3 防止污染策略

* 保持接口单一责任：只定义一个核心抽象方法
* default / static 方法只用于组合或工具
* 避免业务逻辑 / 状态管理混入接口

## 四、default 方法的边界与设计哲学

### 4.1 default 方法优势

* 提供组合方法，提高接口复用性
* 避免工具类臃肿
* 支撑**流水线风格 API**

**示例：Transformer 接口**

```java
@FunctionalInterface
interface Transformer<T> {
    T apply(T t);

    default Transformer<T> andThen(Transformer<T> after) {
        return t -> after.apply(this.apply(t));
    }
}
```

### 4.2 边界与反模式

* 不要在 default 方法中引入复杂业务逻辑
* 避免 default 方法依赖状态
* 避免 default 方法抛出 checked exception

> 核心哲学：default 方法是**接口组合工具**，而非业务逻辑容器。

---

## 五、Checked Exception 的设计陷阱

* Lambda / 方法引用无法直接抛 checked exception
* 常见设计误区：

    * 在接口抽象方法中声明 checked exception
    * 在 default 方法中封装 checked exception

### 5.1 正确处理方式

1. **封装为 RuntimeException**

```java
Function<String, Integer> safeParse = s -> {
    try { return Integer.parseInt(s); }
    catch(Exception e) { throw new RuntimeException(e); }
};
```

2. **自定义带 checked exception 的接口**

```java
@FunctionalInterface
interface CheckedFunction<T, R> {
    R apply(T t) throws Exception;
}
```

* 仅在框架内部处理 checked exception
* 对外暴露标准接口，避免破坏组合能力

> 原则：通用接口尽量不要抛 checked exception，保持可组合性。

## 六、函数式接口在框架 / SDK 中的设计经验

### 6.1 明确语义与类型契约

* 接口名称必须表达核心行为
* 优先复用标准接口作为参数类型

### 6.2 支持组合与流水线

* default 方法提供组合能力
* 提供链式操作，支持高阶函数

### 6.3 控制状态与副作用

* 避免接口方法管理状态
* 保持接口纯函数，便于测试与复用

### 6.4 性能与实例管理

* 非捕获接口实例可复用单例
* 捕获接口实例注意对象开销，高频调用场景需优化

### 6.5 框架案例

* **Stream API**：大量使用标准接口，组合 default 方法
* **CompletableFuture**：回调函数均使用标准接口，避免状态污染
* **自研 SDK / 框架**：保持接口小而纯粹，提供组合 default 方法

---

## 七、总结与架构原则

1. **标准接口优先，除非语义化自定义接口更清晰**
2. **接口单一责任，避免污染**
3. **default 方法仅用于组合，避免复杂业务逻辑**
4. **checked exception 谨慎设计**，保证可组合性
5. **高阶设计原则**：可复用、可组合、轻量对象、类型安全
6. **架构高度思考**：函数式接口是框架的“类型合约”，影响代码组合性和可维护性

> 核心理念：函数式接口不仅是语言特性，更是**高质量框架与 API 设计的基石**。良好的设计可以提高可组合性、可维护性和性能；不良设计则会导致接口污染、组合力下降和调试复杂度提升。
