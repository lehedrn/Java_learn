# Stream 中间操作深度解析：行为、顺序与性能

> **系列定位**：Java 8 Stream API 核心使用篇
> **本篇目标**：不只是“会用中间操作”，而是**真正理解它们是如何执行的**。

---

## 一、为什么要单独讲“中间操作”？

在 Stream API 中，中间操作（Intermediate Operation）是**最容易被误用、也最容易被低估的一部分**。

很多人对 Stream 的理解停留在：

```java
list.stream()
    .filter(...)
    .map(...)
    .collect(...);
```

但真正决定：

* **性能好坏**
* **是否能短路**
* **并行时是否安全**

的，恰恰是这些看似“只是拼接在一起”的中间操作。

> 👉 本篇的关键词只有三个：**惰性、顺序、状态**。

---

## 二、中间操作的本质回顾

先重申一个在第 1 篇中已经建立的结论：

> **中间操作不会触发执行，它们只是在“搭建流水线”。**

它们有三个共同特征：

1. 返回新的 Stream
2. 本身不消费数据
3. 只有在终止操作出现时才会真正执行

理解了这一点，后面的所有行为都会变得“合理”。

---

## 三、filter：短路、顺序与惰性

### 1️⃣ filter 是“逐元素生效”的

```java
list.stream()
    .filter(i -> {
        System.out.println("filter: " + i);
        return i % 2 == 0;
    })
    .forEach(System.out::println);
```

输出结果表明：

* `filter` 并不是先过滤完所有元素
* 而是**一个元素一个元素地判断**

> 这是典型的流水线（Pipeline）模型。

---

### 2️⃣ filter 与短路操作的配合

```java
Optional<Integer> firstEven = list.stream()
    .filter(i -> {
        System.out.println("filter: " + i);
        return i % 2 == 0;
    })
    .findFirst();
```

一旦 `findFirst` 找到结果：

* 后续元素将**不再经过 filter**

> **短路并不是 filter 自己的能力，而是流水线整体的行为。**

---

### 3️⃣ 顺序 Stream 与并行 Stream 的差异

在顺序 Stream 中：

* `filter` 严格遵循元素顺序

而在并行 Stream 中：

* 顺序可能被打乱（除非使用 `forEachOrdered`）

这一点在并行流章节会详细展开，这里只需要记住：

> **filter 本身是无状态的，但顺序感知来自 Stream 类型。**

---

## 四、map vs flatMap（核心重点）

这是 Stream API 中**认知鸿沟最大**的一组操作。

---

### 1️⃣ map：一对一映射

```java
List<String> words = Arrays.asList("hello", "world");

List<Integer> lengths = words.stream()
    .map(String::length)
    .collect(Collectors.toList());
```

`map` 的特征非常明确：

> **输入一个元素，输出一个元素。**

即使输出的是集合，map 也不会“展开”它。

---

### 2️⃣ flatMap：一对多，再“拍平”

```java
List<List<Integer>> list = Arrays.asList(
    Arrays.asList(1, 2),
    Arrays.asList(3, 4)
);

List<Integer> result = list.stream()
    .flatMap(inner -> inner.stream())
    .collect(Collectors.toList());
```

`flatMap` 的本质是：

> **先 map，再 flatten（拍平）。**

如果你用一句话记忆：

* `map`：结构不变，只变内容
* `flatMap`：结构被压平

---

### 3️⃣ 一个典型错误示例

```java
list.stream()
    .map(s -> s.split(""))
    .forEach(System.out::println);
```

很多人期望得到“字符流”，但实际上得到的是：

* `Stream<String[]>`

正确写法是：

```java
list.stream()
    .flatMap(s -> Arrays.stream(s.split("")))
    .forEach(System.out::println);
```

---

### 4️⃣ 为什么 flatMap 是函数式编程的核心操作？

因为它：

* 消除了嵌套结构
* 保持了流水线的线性形态
* 是“组合”的基础

> 在很多函数式语言中，`flatMap` 甚至比 `map` 更重要。

---

## 五、distinct / sorted：隐藏成本

### 1️⃣ distinct：有状态操作

```java
list.stream()
    .distinct()
    .forEach(System.out::println);
```

为了去重，Stream 内部必须：

* 记录已经见过的元素
* 通常依赖 `HashSet`

因此：

> **distinct 是一个有状态中间操作。**

---

### 2️⃣ sorted：全量排序的代价

```java
list.stream()
    .sorted()
    .forEach(System.out::println);
```

`sorted` 的特点：

* 必须等待**所有元素到齐**
* 才能开始排序

这意味着：

* 无法逐元素向下游传递
* 会打断流水线的“流动性”

> sorted 通常是性能拐点操作。

---

## 六、limit / skip：顺序影响结果

```java
list.stream()
    .limit(5)
    .filter(...)
    .forEach(...);
```

与：

```java
list.stream()
    .filter(...)
    .limit(5)
    .forEach(...);
```

这两段代码：

* **语义不同**
* **性能特征也不同**

---

### 一个直观结论

> **操作顺序 ≠ 代码书写顺序**

真正的执行顺序取决于：

* 是否短路
* 是否有状态
* 是否需要全量数据

合理调整 `filter / limit` 的位置，往往能显著减少计算量。

---

## 七、有状态 vs 无状态中间操作

这是理解 Stream 性能与并行行为的分水岭。

### 无状态操作（Stateless）

* filter
* map
* flatMap

特点：

* 不依赖历史元素
* 更容易并行化

---

### 有状态操作（Stateful）

* distinct
* sorted
* limit（在某些场景下）

特点：

* 依赖之前或全部元素
* 可能引入额外内存与同步成本

> **并不是不能用，而是要“有意识地用”。**
