# Java 8 Stream API：从集合操作到声明式数据处理

> **系列定位**：Java 8 新特性系统学习 · Stream API
>
> **本篇目标**：建立对 Stream API 的正确认知与心智模型，而不是记忆 API 用法。

---

## 一、为什么 Java 8 需要 Stream API？

在 Java 8 之前，对集合的处理方式几乎是清一色的 **for 循环 + 临时变量**：

```java
List<Integer> list = Arrays.asList(1, 2, 3, 4, 5);
int sum = 0;
for (Integer i : list) {
    if (i % 2 == 0) {
        sum += i;
    }
}
```

这段代码并不复杂，但它暴露了 Java 传统集合处理方式的几个结构性问题。

### 1️⃣ 关注点混杂

这段代码同时承担了多种职责：

* **业务意图**：筛选偶数、求和
* **控制流程**：循环、条件判断
* **状态管理**：临时变量 `sum`

业务逻辑被淹没在“怎么做”之中，而不是清晰地表达“做什么”。

---

### 2️⃣ 可读性与可维护性不足

随着逻辑复杂度提升（多重条件、排序、分组、聚合），
for 循环往往演化为冗长、难以复用的样板代码。

代码可以运行，但**意图并不直观**。

---

### 3️⃣ 并行化成本极高

如果希望提升性能，引入多线程通常意味着：

* 手动拆分任务
* 处理线程安全
* 合并计算结果

这些工作与业务目标无关，却是不可避免的额外成本。

👉 **Stream API 的引入，本质上是对“集合计算模型”的一次升级。**
它并不是为了取代集合，而是为了让“对数据做什么”本身成为一等公民。

> ⚠️ 提前说明：Stream 并不是所有场景的最优解。
> 在逻辑极其简单或对性能极端敏感的代码中，传统 for 循环依然有其价值。

---

## 二、什么是 Stream？（以及它不是什么）

在学习 Stream 的用法之前，必须先澄清一个核心认知：

> **Stream 不是集合。**

### 1️⃣ Stream ≠ Collection

| 对比维度    | Collection | Stream      |
| ------- | ---------- | ----------- |
| 是否存储数据  | 是          | 否           |
| 是否可变    | 通常可变       | 不可变（不修改源数据） |
| 是否可重复使用 | 是          | 否（一次性）      |
| 关注点     | 数据存储       | 数据计算        |

```java
Stream<Integer> stream = list.stream();
```

这行代码既没有复制数据，也没有触发任何计算。

> 它只是基于数据源，创建了一个**计算视图（view）**。

---

### 2️⃣ 一个典型的误用示例

```java
Stream<Integer> s = list.stream();
s.forEach(System.out::println);
s.forEach(System.out::println); // IllegalStateException
```

这是很多人第一次使用 Stream 时都会遇到的问题。

原因并不复杂：

> **Stream 是一次性的计算过程描述，终止操作执行后即被消费。**

这一点，是理解 Stream 行为的第一道分水岭。

---

### 3️⃣ Stream 的本质总结

可以用一句话来概括 Stream：

> **Stream 是对数据源的一次性、惰性、函数式的计算过程描述。**

* **一次性**：只能被消费一次
* **惰性**：中间操作不会立即执行
* **面向计算**：关注转换、过滤与归约，而非存储

---

## 三、Stream API 的核心设计思想

### 1️⃣ 声明式编程，而不是命令式编程

对比两种写法：

```java
// 命令式
int sum = 0;
for (Integer i : list) {
    if (i % 2 == 0) {
        sum += i;
    }
}
```

```java
// 声明式
int sum = list.stream()
              .filter(i -> i % 2 == 0)
              .mapToInt(Integer::intValue)
              .sum();
```

Stream 写法强调的是：

* **过滤什么**（filter）
* **如何转换**（map）
* **最终结果是什么**（sum）

而不是循环与状态管理的细节。

> 如果说 Lambda 解决的是“如何把行为当作参数”，
> 那么 Stream 解决的就是“如何把数据计算表达成一条流水线”。

---

### 2️⃣ 与函数式接口 / Lambda 的协同设计

Stream API 并不是孤立存在的，它建立在 Java 8 函数式体系之上。

几乎所有 Stream 操作，本质上都依赖函数式接口：

| Stream 操作 | 对应函数式接口             |
| --------- | ------------------- |
| filter    | `Predicate<T>`      |
| map       | `Function<T, R>`    |
| forEach   | `Consumer<T>`       |
| reduce    | `BinaryOperator<T>` |

> **Stream 是 Lambda 最重要的应用场景，而 Lambda 是 Stream 得以成立的前提。**

---

## 四、Stream 的整体使用模型

所有 Stream 程序，都可以抽象为统一的三段式结构：

```text
数据源（Source） → 中间操作（0~N） → 终止操作（1 个）
```

### 1️⃣ 数据源（Source）

* Collection：`list.stream()`
* 数组：`Arrays.stream(arr)`
* I/O：`Files.lines(path)`
* 工厂方法：`Stream.of(...)`

数据源只负责提供元素，不关心如何处理。

---

### 2️⃣ 中间操作（Intermediate Operation）

中间操作的特点：

* 返回新的 Stream
* 不触发执行（惰性）
* 可链式组合

典型操作包括：

* `filter`
* `map / flatMap`
* `distinct`
* `sorted`
* `limit / skip`

它们本质上是在**构建一条计算流水线**。

---

### 3️⃣ 终止操作（Terminal Operation）

终止操作具有决定性意义：

* 触发整个 Stream 的执行
* 消费 Stream
* 返回结果或产生副作用

常见终止操作：

* `forEach`
* `collect`
* `reduce`
* `count / min / max`

一个 Stream **只能有一个终止操作**。

---

## 五、惰性执行与流水线模型

惰性执行是 Stream API 最容易被忽略，但又最关键的特性。

```java
Stream<Integer> stream = list.stream()
    .filter(i -> {
        System.out.println("filter: " + i);
        return i % 2 == 0;
    })
    .map(i -> {
        System.out.println("map: " + i);
        return i * 2;
    });

System.out.println("before terminal");
stream.forEach(System.out::println);
```

通过输出顺序可以发现：

* 中间操作在终止操作之前不会执行
* 每个元素都会依次经过 `filter → map → forEach`

这意味着：

> Stream 采用的是**逐元素的流水线模型**，而不是阶段式批处理。

这一模型为后续的短路操作、并行执行和性能优化提供了基础。
